# ADR-0002：菜谱数据以 JSON 文件为唯一数据源

## 状态

已接受（2026-09-19，实现于 M0–M3）

## 背景

菜谱是**读多写极少**的数据：初期几十道、长期几百道，更新频率以周计，写者只有一个人。但它同时有三个强要求：

1. **可手改**：想快速改个用量、补个小贴士，不该开管理界面。
2. **可备份、可搬机器**：数据是长期资产，应该能整个目录拷走就完成迁移。
3. **可版本化**：改了什么一眼能看见（`git diff` 可读）。

同时要预留演进：将来可能要做网页录入（M5），那时写操作会变多。

## 决策

- **一道菜一个 JSON 文件**：`data/recipes/<id>.json`，`id` 必须等于文件名。
- 服务启动时把全部文件读进内存并建索引；搜索、筛选都在内存里做。
- **只有 `src/server/services/recipe-repository.ts` 读写文件系统**，其他模块不得 import `node:fs`。
- 类型定义在 `src/shared/types.ts`，运行时校验在 `src/server/lib/schema.ts`（zod）：单个文件校验失败**只跳过该文件**并告警，不影响其他菜谱与服务启动。
- 新增字段一律**可选且向后兼容**；旧文件不要求迁移。
- 图片不进 JSON：按 `data/images/<recipe-id>/cover.jpg` 约定用目录匹配。
- 若将来改用 SQLite，**只重写 repository 这一层**，路由与前端不动。

## 备选方案与未选原因

| 方案 | 未选原因 |
| --- | --- |
| SQLite | 当前数据量与写入频率用不上事务与并发控制，反而引入 schema/迁移成本；且二进制文件不可 diff、不可直接手改 |
| Markdown + frontmatter | 需要解析依赖；步骤、食材这类嵌套结构用 JSON 更直接，也更好做校验 |
| 构建期把数据编译进前端产物 | 加一道菜就要重新构建；数据与代码耦合，无法单独备份或手改生效 |
| 独立的菜谱管理后台 | 目前没有录入需求；先把"看"做顺，写操作等 M5 再立规格（属 T2，需要新 ADR） |

## 后果

好处：数据可以整体打包备份、可以 Git 版本化、手改即时生效、容器随时重建不丢数据；新增字段的兼容性风险被限制在"可选字段"这一条纪律上。

代价：没有事务与并发写（在单人、低频写入下不成立）；全量载入内存（千道菜量级仍是毫秒级）；文件名与 `id` 必须一致，靠校验兜住。

需要注意：M5 若引入网页写入，会改变"写者只有一个进程"的前提——那时必须新开 ADR，讨论并发写、写入失败与文件锁。
