# ADR-0005：菜谱内容变为可写（编辑模式 + 修改记录）

## 状态

**提议中**（2026-09-21）—— 待用户批准；批准前不写实现。关联规格：[CB-009](../features/CB-009-edit-mode.md)。

## 背景

[ADR-0002](ADR-0002-json-files-as-source-of-truth.md) 的前提是"**写者只有一个人，运行期只读**"：应用启动把 `data/recipes/*.json` 读进内存，运行期只写日志。之后 [ADR-0003](ADR-0003-write-operations-user-state.md) 开了一个口子，但那是**用户状态**（点赞/收藏/厨具），与菜谱内容分开存，菜谱仍然只读。

现在用户要求在浏览器里**直接修改菜谱内容**（"增加个可编辑的模式，就是我可以对内容做修改"），并要求**留修改记录**（"修改后要有一个修改记录"）。这直接改变了 ADR-0002 的那条前提：

- 应用运行期要写 `data/recipes/<id>.json` —— 这是**内容数据**（用户的长期资产、要在 git 里可 diff、要能整体备份），不是状态；
- 出现**并发写**的新形态：网页编辑 + 手工编辑器 + 导入脚本都可能改同一个文件；
- 写坏了是**内容损坏**，比状态损坏更严重（菜谱是「照着做」的依据）。

按 [决策记录规范](README.md)，这属于必须写 ADR 的变更（改数据源的可写性）。

## 决策

### 1. 写路径：仍在唯一的入口，整份替换

- 新增 `PUT /api/recipes/:id`，body = `{ recipe: <整份菜谱>, baseRevision: <客户端加载时的版本> }`。
- 写入落在 **`recipe-repository.ts`**（本项目唯一的数据访问入口，见 [ARCHITECTURE §4](../ARCHITECTURE.md)）；其他模块不碰文件。
- **写整份、不做字段补丁**：zod 校验、历史快照、并发判定都是整份粒度的（简单、可验证）。
- 用 `PUT` 而不是 `POST`：这是**幂等的整份替换**（同一份内容重复提交结果相同），与 like/favorite 那种"动作"不同。ADR-0003 §4 的"只接受 POST"是针对当时的动作式接口，这里记录该差异。

### 2. 写入前必须过同一份校验

复用 `src/server/lib/schema.ts` 的 `createRecipeSchema`（含厨具词表、tag 词表校验）：
**不合法就 400 + 可定位的报错**（`steps.0.text: 步骤内容不能为空` 这种），**绝不写盘**。
理由：网页编辑不能成为"绕过数据纪律"的入口 —— `npm run check:data` 能拦住的，接口也必须拦住。

### 3. 原子替换 + 失败回滚

- 写临时文件 → `rename` 覆盖（同一目录内），避免半个文件；
- 写盘失败（磁盘满/只读）→ 内存里的索引**保持原样**，接口返回 503；
- 成功后**内存索引立即更新**（不要求重启），列表/详情/搜索马上反映新内容。

### 4. 版本守卫：不静默 last-write-wins

- 详情接口返回 `revision`（**文件内容的哈希**，不是 `updatedAt` —— 手工改文件不会更新 `updatedAt`，哈希才靠得住）。
- 保存时提交 `baseRevision`；与当前不一致 → **409**，响应带上服务端当前版本 + 当前 `revision`。
- 前端必须让用户**看到冲突并做选择**（重新加载丢掉自己的改动 / 用我的覆盖 / 打开两份自己看），**不允许静默覆盖**。
  这条与 CB-008 的并发教训同源：界面显示的内容与磁盘不一致，是必须避免的失败。

### 5. 修改记录 = 被替换版本的快照

- 每次保存前，把**即将被替换的那一份**存成快照：`data/history/recipes/<id>/<ISO 时间戳>-<来源>.json`。
- 来源取值：`manual`（网页编辑）、`llm-merge`（CB-010 的 LLM 合并提案落地）、`import`（导入/同步覆盖）、`restore`（从历史恢复）。
- 菜谱 JSON 里写 `updatedAt`（ISO 日期）。
- **不自动删除历史**：文本很小（单份 2–5 KB），自动清理属于数据删除，需要单独授权（T3）。
- 历史是**内容数据**，随 `data/` 一起备份；它在 git 里可 diff，等于给编辑又加了一层记录。

### 6. 明确不做（本 ADR 边界内）

- 不做图片上传（另立规格）；
- 不做多用户/权限（局域网自用，与 ADR-0003 同一信任模型：**没有鉴权**，能访问局域网就能编辑）；
- 不做实时协同编辑（两人同时改由 §4 的 409 兜住，不做合并 UI）；
- 不做批量编辑。

### 7. 与导入/同步的关系（重要）

`scripts/import-howtocook.ts` 现在是"**直接覆盖** `data/recipes/<id>.json`"。一旦菜谱可编辑，这个行为就危险了（会吃掉网页修改）。
因此本 ADR 同时约定：**导入脚本在 CB-010（来源基线 + 合并）落地前，必须在文档与脚本输出里明确标注"会覆盖本地修改"**；落地后，导入统一走「先比较、后合并」的流程。

## 后果

### 好处

- 手机/电脑就能改菜谱（不用 ssh + 编辑器），改完立刻生效；
- 改错能回滚（历史快照 + git 两重）；
- 内容纪律没有放松（写入也必须过同一份 zod 校验）。

### 代价与必须接受的风险

1. **内容数据变可写** —— 网页编辑、手工编辑器、导入脚本三方都能改同一个文件。兜底手段：原子替换 + 版本守卫（409）+ 历史快照；**没有**文件锁（单进程假设，见 ADR-0003）。
2. **没有鉴权** —— 局域网内任何设备都能改菜谱。与既有只读接口同一信任模型；若要公网访问必须先补鉴权（新 ADR）。
3. **历史会累积** —— 每次保存多一份快照，长期会有几千个小文件（可接受：文本、可整体删除但需授权）。
4. **`updatedAt` 不可靠** —— 它只是"经过应用保存过"的标记，不是并发判断依据（并发判断看内容哈希）。

### 需要注意

- 容器与部署：`data/` 已经是可写挂载（ADR-0003 改过），**本次不需要改 compose**；
- 备份：`data/` 一起打包即可（历史与菜谱都在里面）；
- 回滚：删掉写接口即可回到只读；已经写过的内容留在文件里，不受影响。
