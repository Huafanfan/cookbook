# ADR-0005：菜谱内容变为可写（编辑模式 + 修改记录）

## 状态

**已接受**（2026-09-21：用户批准方向；预实现复核的 5 条阻断项已修 —— 并发保证范围、提交点与失败语义、独立 `historyId`、409 重试守卫、导入器默认拒绝覆盖）。关联规格：[CB-009](../features/CB-009-edit-mode.md)。

## 背景

[ADR-0002](ADR-0002-json-files-as-source-of-truth.md) 的前提是"**写者只有一个人，运行期只读**"：应用启动把 `data/recipes/*.json` 读进内存，运行期只写日志。之后 [ADR-0003](ADR-0003-write-operations-user-state.md) 开了一个口子，但那是**用户状态**（点赞/收藏/厨具），与菜谱内容分开存，菜谱仍然只读。

现在用户要求在浏览器里**直接修改菜谱内容**（"增加个可编辑的模式，就是我可以对内容做修改"），并要求**留修改记录**（"修改后要有一个修改记录"）。这直接改变了 ADR-0002 的那条前提：

- 应用运行期要写 `data/recipes/<id>.json` —— 这是**内容数据**（用户的长期资产、要在 git 里可 diff、要能整体备份），不是状态；
- 出现**并发写**的新形态：网页编辑 + 手工编辑器 + 导入脚本都可能改同一个文件；
- 写坏了是**内容损坏**，比状态损坏更严重（菜谱是「照着做」的依据）。

按 [决策记录规范](README.md)，这属于必须写 ADR 的变更（改数据源的可写性）。

## 决策

### 1. 写路径：仍在唯一的入口，整份替换

- 新增 `PUT /api/recipes/:id`，body = `{ recipe: <整份菜谱>, baseRevision: <客户端加载时的版本> }`。
- 写入落在 **`recipe-repository.ts`**（本项目唯一的数据访问入口，见 [ARCHITECTURE §4](../ARCHITECTURE.md)）；其他模块不碰文件。
- **写整份、不做字段补丁**：zod 校验、历史快照、并发判定都是整份粒度的（简单、可验证）。
- 用 `PUT` 而不是 `POST`：这是**幂等的整份替换**（同一份内容重复提交结果相同），与 like/favorite 那种"动作"不同。ADR-0003 §4 的"只接受 POST"是针对当时的动作式接口，这里记录该差异。

**并发保证范围（必须写清楚，不能含糊）**：

- **保证**：应用内对同一道菜的写入是**串行**的 —— 保存操作放在**每菜谱一条串行队列**里（与 ADR-0003 的 user-state 队列同一做法），在队列任务**内部**做：重新读盘 → 算完整 SHA-256 → 比对 `baseRevision` → zod + 内容检查 → 写历史快照 → 临时文件 + rename → 更新内存。队列让"同一进程内的两个保存"不可能交错。
- **不保证**（如实写清）：**外部写者**（手工编辑器、脚本、`scp`、导入器）与应用之间**没有**文件锁。"读盘比哈希再 rename"存在 **TOCTOU 窗口**：在比完哈希与 rename 之间，外部写入的版本仍会被覆盖。因此：**要手工改文件就先停服**（或改用网页编辑）；导入/同步必须走同一受控写入口（见 §7）。规格与文档里**不得宣称**能阻止外部编辑器同时覆盖。

### 2. 写入前必须过同一份校验（两层，缺一不可）

1. **zod 结构校验**：复用 `src/server/lib/schema.ts` 的 `createRecipeSchema`（含厨具词表、tag 词表校验）；
2. **内容检查**：`createRecipeSchema` **不包含** `check:data` 的全部内容检查（`content-lint.ts` 的阻止性问题，如文案分钟数与 `minutes` 不一致），保存时必须**同时**跑它；

**两层都在服务端执行**（不能只在 UI 禁用按钮）：不合法就 400 + 可定位的报错（`steps.0.text: 步骤内容不能为空` 这种），**绝不写盘**。
理由：网页编辑不能成为"绕过数据纪律"的入口 —— `npm run check:data` 能拦住的，接口也必须拦住。

**受保护字段**（不由表单决定，服务端保留当前文件里的值或忽略客户端提交值）：`sourceRef`（来源基线，CB-010）、图片相关派生字段（`coverImage`/`stepImages`，来自扫描）、以及响应里的 `revision`。**`recipe.id` 必须等于 URL 里的 id**（禁止靠改 id "另存一道菜"）。请求体用严格 schema（未知字段拒绝），避免 zod 默认"静默丢掉多余键"。

**暴露面与请求限制**（无鉴权内容写入的风险高于点赞，必须补基本防线）：保持现有端口与只读访问面不变；写接口额外要求 **同源**（校验 `Origin`/`Sec-Fetch-Site`，不通过则 403）、`content-type: application/json`、**请求体大小上限**（单道菜 256 KB 足够）。不新增监听地址、不新增对外接口面。

### 3. 原子替换 + 失败回滚 + **提交点明确**

- 写临时文件 → `rename` 覆盖（同一目录内），避免半个文件；
- 写盘失败（磁盘满/只读）→ 内存里的索引**保持原样**，接口返回 503；
- 成功后**内存索引立即更新**（不要求重启），列表/详情/搜索马上反映新内容；
- **提交点 = 当前菜谱文件 `rename` 成功**。历史快照与当前文件是**两个文件，不是一个原子事务**，因此失败语义必须分开写清：

| 失败位置 | 磁盘状态 | 语义与提示 |
| --- | --- | --- |
| 历史快照写失败 | **当前菜谱文件不变** | 整次保存失败（宁可不保存，也不要"改了但留不下记录"）；提示"没能保存，内容未变" |
| 历史成功、当前文件替换失败 | 多出一条**未完成操作**的历史记录（`afterRevision` 为空或标 `failed`） | 保存失败；提示"没能保存，内容未变"；该历史记录**保留**并在语义上标明是失败的尝试（不假装成功过） |
| 替换**成功之后**再出错（如响应丢失、客户端断开） | 磁盘已经是新内容 | **不得**提示"已恢复原状"；提示"**保存结果未确认，请刷新查看**"，前端刷新后以服务端为准 |

### 4. 版本守卫：不静默 last-write-wins

- 详情接口返回 `revision`（**文件字节的完整 SHA-256**，不是 `updatedAt` —— 手工改文件不会更新 `updatedAt`，哈希才靠得住）。
- 保存时提交 `baseRevision`；与当前不一致 → **409**，响应带上服务端当前版本 + 当前 `revision`。
- 前端必须让用户**看到冲突并做选择**（重新加载丢掉自己的改动 / 用我的覆盖 / 打开两份自己看），**不允许静默覆盖**。
- **"用我的覆盖"也要过守卫**：用户确认后，前端必须带上**服务端刚返回的最新 `currentRevision`** 重新提交，**不是**直接 force-write；若在此期间又有人改，**继续 409**（可反复）。草稿始终保留在本地，不因冲突而丢。
  这条与 CB-008 的并发教训同源：界面显示的内容与磁盘不一致，是必须避免的失败。

### 5. 修改记录 = 被替换版本的快照

- 每次保存前，把**即将被替换的那一份**存成快照：`data/history/recipes/<id>/<时间戳>-<historyId>-<来源>.json`。
- **`historyId` 独立且唯一**（时间戳 + 随机短串，创建时**独占**：`wx` 标志，撞名就换一个）—— **不能拿内容 `revision` 当历史 ID**：同一内容会被保存多次，revision 会重复。
- 记录格式（自描述，便于以后迁移）：

```json
{
  "historyId": "20260921T143305Z-7f3a",
  "recipeId": "ang-ci-yu-dou-fu-tang",
  "beforeRecipe": { "…": "被替换掉的整份内容" },
  "beforeRevision": "sha256:9f2c…",
  "afterRevision": "sha256:1b7d…",
  "savedAt": "2026-09-21T14:33:05.000Z",
  "source": "manual",
  "note": "盐改成 4g",
  "outcome": "replaced"
}
```

- `source` 取值：`manual`（网页编辑）、`llm-merge`（CB-010 的 LLM 合并提案落地）、`import`（导入/同步覆盖）、`restore`（从历史恢复）。`outcome` 取值 `replaced` / `failed`（见 §3 的失败语义）。
- 菜谱 JSON 里写 `updatedAt`（ISO 日期）。
- **不自动删除历史**：文本很小（单份 2–5 KB），自动清理属于数据删除，需要单独授权（T3）。
- 历史是**内容数据**，随 `data/` 一起备份；它在 git 里可 diff，**但不要承诺"历史已经进入 Git"**：磁盘上有记录 ≠ 已提交（提交是人工/别处的动作）。

### 6. 明确不做（本 ADR 边界内）

- 不做图片上传（另立规格）；
- 不做多用户/权限（局域网自用，与 ADR-0003 同一信任模型：**没有鉴权**，能访问局域网就能编辑）；
- 不做实时协同编辑（两人同时改由 §4 的 409 兜住，不做合并 UI）；
- 不做批量编辑。

### 7. 与导入/同步的关系（重要）

`scripts/import-howtocook.ts` 现在是"**直接覆盖** `data/recipes/<id>.json`"。一旦菜谱可编辑，这个行为就危险了（会吃掉网页修改）。
本 ADR 约定：

1. **导入器默认拒绝覆盖已存在的菜谱**：需要显式开关（如 `--overwrite-existing`）才会覆盖，并在输出里列出"将被覆盖的 id"让人确认；**只贴一行警告不算**（复核意见 P5）。
2. **"覆盖导入"与"运行中编辑"互斥**：跑覆盖导入前先停服（或至少确认没有正在编辑的会话），文档里写明操作顺序。
3. CB-010（来源基线 + 合并）落地后，导入统一走「先比较、后合并」的流程；在此之前，覆盖导入只是**逃生舱**，不是常规手段。

## 后果

### 好处

- 手机/电脑就能改菜谱（不用 ssh + 编辑器），改完立刻生效；
- 改错能回滚（历史快照 + git 两重）；
- 内容纪律没有放松（写入也必须过同一份 zod 校验）。

### 代价与必须接受的风险

1. **内容数据变可写** —— 网页编辑、手工编辑器、导入脚本三方都能改同一个文件。兜底手段：原子替换 + 版本守卫（409）+ 历史快照；**没有**文件锁（单进程假设，见 ADR-0003）。
2. **没有鉴权** —— 局域网内任何设备都能改菜谱。与既有只读接口同一信任模型；若要公网访问必须先补鉴权（新 ADR）。
3. **历史会累积** —— 每次保存多一份快照，长期会有几千个小文件（可接受：文本、可整体删除但需授权）。
4. **`updatedAt` 不可靠** —— 它只是"经过应用保存过"的标记，不是并发判断依据（并发判断看内容哈希）。

### 需要注意

- 容器与部署：`data/` 已经是可写挂载（ADR-0003 改过），**本次不需要改 compose**；
- 备份：`data/` 一起打包即可（历史与菜谱都在里面）；
- 回滚：删掉写接口即可回到只读；已经写过的内容留在文件里，不受影响。
