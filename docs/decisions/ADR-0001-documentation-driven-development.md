# ADR-0001：采用文档驱动的规格先行开发

## 状态

已接受（2026-09-19）

## 背景

这个项目是**单人自用**、跨多个 session 断续开发的。开工时（2026-09-19）已经出现过一次典型情况：界面"看起来不错"并不等于"站在灶台前顺手"——步骤粒度、字号、按钮位置这些问题，只有在真实做菜时才知道好坏。代码里看不出产品意图，聊天上下文又会丢失，于是很容易出现两种浪费：

1. 改了半天界面，却没解决真实卡点；
2. 后一个 session 不知道前一个为什么这么设计，凭感觉改，把已经权衡过的决定推翻。

同时，菜谱数据（`data/recipes/*.json`）是用户长期积累的资产，字段一旦随意变更就会污染内容。

## 决策

- 文档是产品意图、边界与验收标准的事实来源，代码是实现；文档不逐行复述代码。
- 根目录 `AGENTS.md` 是后续 session 的执行门槛；`docs/START-HERE.md` 是当前状态与阅读路径的入口。
- 变更分级：T0（无行为变化）无需规格；**T1 及以上必须先有状态为 `accepted` 的功能规格**；T2 还需 ADR；T3 需要用户明确授权。
- 功能规格使用 `draft` → `accepted` → `implemented` → `verified`（被替代则 `superseded`）生命周期，并在实现后回填代码路径与验证证据；没有证据不得标记 `verified`。
- **一条事实只保留一个权威位置**，其他文档用链接引用（清单见 `docs/START-HERE.md`）。发现两处说法不一致时，先修权威位置，再修引用。
- T1/T2 默认"先文档提交，再实现提交"；用户要求压缩历史时，仍不得在规格 `accepted` 之前编辑实现。
- 涉及厨房使用的改动（做菜模式、步骤展示、字号、计时），**以试做反馈作为验收判据**，记录在 `docs/features/CB-001-cooking-feedback.md`。
- 实现与规格不一致时暂停收尾：说明差异，选择改规格或改实现；不得把文档静默改写成代码已经发生的行为。

## 后果

后续 session 可以从仓库内的文档恢复项目上下文，而不是依赖聊天记忆；设计、实现与验收之间有可追溯的链路；给菜谱数据加字段之前会先在 `DATA_MODEL.md` 里被审一遍，避免污染长期数据。

代价是每个有行为变化的改动都要先写规格再写代码，速度看起来慢一点。为控制负担：ADR 只用于跨模块或难逆转的选择；纯文案、样式微调走 T0 轻量流程；模板里的章节即使"无"也要求写明，避免漏掉该问的问题（例如失败降级与向后兼容）。

静态检查（typecheck/test/check:data）可以证明实现没坏，但**不能判断语义是否正确、是否真的顺手**——文档复核与试做仍是每个变更的必要步骤。
