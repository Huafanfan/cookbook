# ADR-0009：创意工坊采用本地草稿、DS 整理与受控新建

## 状态

已接受（2026-10-01）。关联 [CB-014 规格](../features/CB-014-recipe-workshop.md)；用户要求开始实施、持续更新文档、提交推送，界面完成后部署供 review。

## 背景

用户希望用链接、一组图片及其他方式录入新菜，指定网站 LLM 使用本地 DS 环境变量。现有功能能编辑已有菜并保留历史，但新建、素材上传与服务端多模态整理尚未实现。

不同输入都会产生不完整、可能冲突的候选；直接要求模型生成一份合法 `Recipe` 容易把必填份量、难度与未知数字填成猜测。另一方面，正式菜谱仍应保持 [ADR-0002](ADR-0002-json-files-as-source-of-truth.md) 的 JSON 数据形态，并遵循 [ADR-0005](ADR-0005-editable-recipes-and-history.md) 的集中写路径、校验与明确提交点。

本决策扩展 CB-007 的上传范围、CB-009 的新建范围和 [ADR-0006](ADR-0006-source-baseline-and-llm-resync.md) 的“仅脚本 LLM”边界；不改变其已接受功能的行为。用户明确指定 DS，为本功能的最小模型请求提供出站授权；用户提供公开链接并点击整理时，才触发对应来源抓取。应用仍只在局域网提供访问。

## 决策

### 1. 一套材料与草稿流程，保持正式 Recipe 格式

范围与交互以 [CB-014 §1–§5](../features/CB-014-recipe-workshop.md#1-目标与非目标) 为准。来源提取器输出统一材料，不各自创建一套保存逻辑：

```text
材料 → 本地提取/检查 → DS 或确定性解析 → 不完整候选与依据
    → 人工校对 → 正式 Recipe 校验 → repository 创建 → 现有菜谱功能
```

- 正式 JSON 首版不加字段。`source` 记录作者/原链接/整理说明；不虚构 `sourceRef` 的仓库路径、commit 或基线。
- 工坊记录独立保存来源与原始素材，通过 `savedRecipeId` 关联正式菜谱。候选可有未知字段，正式保存必须满足当前完整 schema。
- 模型只返回候选、待确认项和材料引用；系统生成 ID、创建时间和磁盘路径。模型没有工具、目录浏览或保存权。

### 2. 草稿在服务端持久化，所有资产读写经 repository

目录如下，全部位于已有数据挂载中：

```text
data/workshop/drafts/<draft-id>/draft.json
data/workshop/drafts/<draft-id>/sources/<source-id>.<允许的扩展名>
data/recipes/<recipe-id>.json                         # 正式提交点
data/images/<recipe-id>/{cover.jpg,step-N.jpg}        # 人工采用的配图
```

- 文件读写、临时文件、素材存取和新建均落在 `recipe-repository.ts`，不新增通用文件访问模块。提取、图片处理和 LLM 客户端只接收内存里的文本/字节，不 import `node:fs`。
- 草稿修改按草稿串行队列与 revision 守卫；素材 ID 由服务端生成，原文件名只作为显示信息。素材路由通过记录定位文件，不接受客户端路径。
- 任务状态、来源 revision、用户编辑和创建意图落盘。重启将仍在执行的模型任务标为中断，等待用户重试，不自动重复收费请求。
- 草稿和素材随 `data/` 备份；首版不自动清理、不新增删除接口。空间不足拒绝新素材，保留已有资产；以后清理另定范围并取得删除授权。

草稿字段的权威契约见 [DATA_MODEL §9](../DATA_MODEL.md#9-创意工坊草稿与新建cb-014)；以下仅索引职责，不复制字段定义：

| 项 | 含义 |
| --- | --- |
| `version`、`draftId`、`createdAt`、`updatedAt` | 工坊记录格式版本与系统元数据 |
| `sources` | 服务端 source ID、种类、顺序、选择状态、公开 URL/标题/作者、材料哈希与本地素材引用；不存 Cookies 或鉴权信息 |
| `candidate` | 允许缺项的 Recipe 候选，不包含可由模型控制的路径或受保护字段 |
| `evidence`、`unresolved` | 字段路径到材料/片段的引用、用户补充、整理建议与冲突；引用便于核对，不视为正确性证明 |
| `generation` | 来源版本、模型、提示词/提取器版本、任务状态、内容指纹与 token 用量；不存密钥或原始鉴权头 |
| `creation`、`savedRecipeId` | 幂等键、目标新菜 ID、最终内容哈希、采用图片清单与阶段；用于提交结果恢复 |

### 3. DS 只在服务端使用，调用预算明确

- 从应用进程环境读 `DS_BASE_URL` 与 `DS_AUTH_TOKEN`；默认模型 `deepseek-flash`。可选 `DS_MODEL` 只有在相应文本/图片能力验证通过后使用，配置失败不切到别的提供方。
- Node fetch 调用 OpenAI 兼容 Chat Completions；文本/图片用 `user` 内容块；图片先经本地检查，再以内联 base64 传入，避免模型自行下载任意地址。
- 首版整理采用 `thinking: {"type":"disabled"}` 与 `response_format: {"type":"json_object"}`，给定明确契约并限制输出。旧 CB-010 Luna 客户端保持原协议，不借用其 `reasoning_effort` 配置。
- 只发送本草稿选中材料、必要词表和候选，日志记录状态、用量与诊断代号；不记录鉴权头、完整环境、原始 base64 或提供方完整响应正文。
- JSON 解析、候选 schema、词表与正式内容检查分别执行。用量/时间等关键数字与来源核对，提示词和结构校验不能证明语义准确。
- 每次用户触发整理，模型请求最多 2 次，包含首次与至多一次瞬时故障重试或格式修复；鉴权/模型能力错误不重试。整次操作超时 90 秒，超时后保留草稿；两次调用 token 用量累加。
- 全服务同时执行 1 个整理任务，最多排队 2 个；重复请求复用任务。按有序来源内容哈希、材料选择、用户补充、模型与提示词版本建立指纹，仅同一版本复用成功结果。来源/编辑版本变化使旧结果失效。
- UI 显示本次材料数量与调用状态；记录真实 token 用量。没有样例前不承诺固定耗时或“每道菜只花某个金额”。

### 4. 来源提取与素材范围受限

- 页面先解析 `Recipe` JSON-LD（含 `@graph`、多配方和分组步骤），再用正文提取兜底；公开 Markdown 走现有解析经验。多配方先选择，不以“第一个对象”冒充用户指定菜。
- 普通网页只允许 http/https 公网地址，拒绝带用户凭据的 URL 与非标准 Web 端口。解析所有 IPv4/IPv6 地址，阻断回环、私网、链路本地、保留地址和 IPv4 映射等变体；每跳重定向重验，连接绑定已检查地址，防止 DNS 检查与实际连接之间的重绑定。
- 采用独立的有界提取客户端，不用浏览器执行页面脚本、不加载页面子资源、不借用浏览器登录态。DS 的配置端点由服务端可信配置指定，来源 URL 不得改变提供方端点。
- 建议每草稿最多 5 个链接、12 张图片，最终文本合计 4 万字符；单网页读取上限 2 MiB、15 秒、最多 3 次重定向。超限必须可见，不静默截掉末尾步骤。
- 单原始图片最多 10 MiB，单草稿原始素材合计最多 30 MiB，解码像素上限 1600 万（实施前确认既有容器 256 MiB，采用串行解码与关闭 sharp 缓存来限制峰值）；发送 DS 的处理后图片单张最多 2 MiB、总计最多 16 MiB。按字节签名及实际解码检查，不信任扩展名/MIME；用户提供长图时保留可读细节，达不到时提示拆图。
- 大素材使用独立路由限制，不能调大所有 API 的 bodyLimit；文本/JSON 超限返回具体错误。受限页面给文字/截图出口，不引入第三方云提取兜底。
- 所有提取文本和 HTML 都是数据；React 用普通文本展示。材料中的“忽略规则”等指令不得改变系统契约、调用工具或触发文件执行。
- 截图默认作为原材料，不作正式图片。首版人工采用的自有照片转换为 JPEG、纠正方向、移除 EXIF 等元数据并按现有命名输出；第三方图的来源审核和署名继续引用 ADR-0007/0008，工坊不会自动完成既有静态署名页之外的署名发布。

### 5. 新建不覆盖，明确提交点与恢复

复用既有正式校验和 per-recipe 写队列，但新建有自己的协议，不能用 PUT 替换现有菜：

1. 在草稿锁中检查 `baseRevision`、审阅状态和幂等键；固定候选、服务器生成的新 ID、采用图片及哈希，并持久化创建意图。
2. 在新菜锁中执行完整 zod/词表/内容检查；路径由受控 ID 生成。现有菜谱文件或冲突的图片目录存在则拒绝，不能用“先检查再 rename”假装保证不覆盖。
3. 准备采用图片到独立新目录，完成后才允许正式菜谱提交；失败时草稿保留，尚未出现正式菜谱。崩溃留下的准备素材按创建意图识别，不自动清空数据目录。
4. 写完整临时 JSON，以文件系统的排他创建方式发布正式文件，例如同挂载上的临时文件 `link` 到最终名称，`EEXIST` 即冲突。**正式菜谱文件成功创建是提交点**，普通可覆盖的 rename 不能用于这个最终新建步骤。
5. 提交后更新内存索引和草稿回执。任何后续失败不得说成“没有保存”：启动/重试依据意图、目标 ID 与最终内容/图片哈希核实；匹配则补回执并返回同一 recipe ID，不匹配则报冲突。

- 同一幂等键重试只能得到相同结果；成功后再编辑通过已有 CB-009 PUT 和历史协议，不能在创建重试中修改最终内容。
- 新建前不存在旧版本，不制造一条假的“历史旧菜”；创建依据保留在工坊记录，首次后续编辑才产生正常历史快照。
- 同进程草稿和新菜锁遵循固定顺序，集成时用故障测试检查死锁与重试。现有对外部手工编辑的并发限制仍按 ADR-0005 描述，不宣称新增分布式文件锁。

### 6. 依赖取舍与实施边界

| 能力 | 已采用 | 现有能力是否足够 |
| --- | --- | --- |
| DS、URL、JSON、词表与 API | 复用 Node fetch / URL、Fastify、zod | 足够；不新增模型 SDK、路由库或数据库 |
| 网页正文 | `@mozilla/readability` + jsdom（由开发依赖转生产依赖），禁用脚本与资源加载 | 正则剥 HTML 难可靠处理正文与嵌套结构；URL 抓取使用原生 HTTP/HTTPS 固定已验证 DNS 地址 |
| 上传解析 | 专用 JSON/base64 请求，仅来源上传路由扩大体积上限 | 不新增 multipart 依赖；解码前检查编码长度，具体 API 见 DATA_MODEL |
| 图片解码/规范化 | `sharp` 内存字节接口，串行解码、禁用缓存 | 实际解码验证尺寸/格式、旋转去 EXIF、规范化 JPEG；不让客户端压缩替代服务端检查 |
| PDF/Word/ASR/视频 | 首版不安装；分别评估本地解析、whisper.cpp、FFmpeg | 无当前生产链路，不为尚未实施的方式提前引入常驻服务 |

新增依赖已用 fixture 验证；linux/amd64 镜像结果与体积在 DEPLOYMENT 登记。将来音视频要先评估本地硬件和部署影响，另获范围批准。

## 后果

- 多种来源共用一个审阅与保存流程，新的输入适配器可追加；用户能用截图/文字继续同一草稿，不被平台抓取失败卡住。
- 旧菜谱格式、编辑历史和 LAN 访问保持现有机制；没有强制数据迁移。首版所有服务模块的数据访问继续经过 repository。
- 草稿、原材料与待确认项增加存储和任务恢复复杂度；服务器拥有新的收费出站能力，需要有界队列与请求预算。
- 新建菜谱与图片跨多个文件，没有数据库事务；排他提交与持久化意图可核实故障结果，但必须用临时目录故障注入验证，不能仅靠方案文本宣称可靠。
- 没有自动删除，资产可能逐渐增长；需记录素材占用，清理将是另一个明确授权的功能。
- 主要质量成本仍是数字与做法校对。协议小样成功不代表所有网页、图片、手写或视频都已支持，验收依据以 CB-014 为准。

实施时在 ARCHITECTURE/DEPLOYMENT 中登记模块、出站范围、DS 环境注入和备份。实施、部署、真实手机使用与厨房试做分别留证，不合并成一个“已完成”。
