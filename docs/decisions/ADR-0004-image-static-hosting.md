# ADR-0004：从数据目录托管菜谱图片（`/images/*`）

## 状态

**已接受**（2026-09-20，用户批准首版口径：原图 + 懒加载，不做缩略图/上传/部署）。

## 背景

M4 要做图片展示：列表卡片封面、详情页头图、步骤配图。图片**已经**在 `data/images/<recipe-id>/cover.jpg`（179 张，56 MiB，不进 git、不进镜像），约定见 [DATA_MODEL §4](../DATA_MODEL.md)。

这带来一个此前没有的情况：**要把数据目录里的一类文件通过 HTTP 暴露给浏览器**。既有边界是：

- 菜谱内容只读、只经 `/api/*` 返回 JSON（[ADR-0002](ADR-0002-json-files-as-source-of-truth.md)）；
- 唯一对外暴露的静态资源是前端构建产物（`dist/client`，容器内只读）；
- 容器根文件系统 `read_only: true`，数据目录 bind mount 到 `/data`；运行期唯一的写操作是 `user-state.json`（[ADR-0003](ADR-0003-write-operations-user-state.md)）。

按 [决策记录规范](README.md)，**改变网络暴露面**要写 ADR。本决定不引入写操作、不引入新依赖、不改数据格式，但确实新增了一条对外可读的路径。

## 决策

### 1. 图片由同一个 Fastify 进程托管，不引入额外组件

`@fastify/static` 再注册一次（`prefix: "/images/"`，`root: <dataDir>/images`），**不引入 nginx/CDN/对象存储**。

- 第二次注册必须 `decorateReply: false`（`sendFile` 已由前端静态注册占用），否则启动即报错。
- 根目录不存在（全新部署还没放图片）**不让服务起不来**：只告警，全部走占位图。

### 2. 暴露面是**白名单**，不是"整个目录"

只允许这两类路径：

| 允许 | 说明 |
| --- | --- |
| `/images/<recipe-id>/cover.jpg` | 封面 |
| `/images/<recipe-id>/step-<N>.jpg` | 第 N 步配图 |

- 用 `allowedPath` 对照**启动扫描产出的白名单集合**（扫描认下的文件才在集合里），不靠"目录里只有这些文件"的假设。
  这样路由与 API 严格一致：**API 不给的地址，路由也不提供** —— 越界步骤号、没有对应菜谱的目录、认不出的文件名自动落空。
- **关闭目录列表**（不设 `list`）；`list: false` 下目录请求不返回列表。
- 隐藏文件、非白名单扩展名（`cover.png`、`notes.md`、`.DS_Store`）、越界步骤号一律 **404**。
- **缺失路径必须返回真实 404**：`src/server/index.ts` 的 SPA 兜底当前会把任何 GET 交回 `index.html`（200，`text/html`），必须对 `/images/*` 显式排除——否则"图片 404"会变成"浏览器拿到一坨 HTML"，还可能被当成图片缓存下来。

### 3. 缓存语义：`no-cache` + ETag 条件请求

- 图片响应 `Cache-Control: no-cache`，保留 `ETag`/`Last-Modified`，靠 **304 重验证**省流量。
- **不采用"启动时读 mtime 拼 `?v=` + 一年 `immutable`"**：那个版本号只反映**启动时刻**的文件状态，并没有和响应内容绑定。替换 `cover.jpg` 后不重启，URL 不变 → 浏览器一年内都不会再问服务器 → 与项目既有立场（"改了东西刷新就能看到，不需要手动清缓存"，见 `index.ts` 的缓存策略注释）直接冲突。

### 4. 目录匹配仍在服务端，菜谱 JSON 不写图片路径

沿用 ADR-0002 的"约定目录匹配"：启动扫描 `data/images/`，把存在的封面/步骤图匹配到菜谱 id；**不新增菜谱文件字段**，不改 `data/recipes/*.json`。

- 扫描放在**既有**的唯一数据访问入口 `recipe-repository.ts`，不新增第 6 处文件系统访问模块（见 [ARCHITECTURE §4](../ARCHITECTURE.md)）。
- 未识别文件名、步骤号越界、图片目录没有对应菜谱：**只告警**，不影响启动与其他菜谱（与坏菜谱文件的处理一致）。

### 5. 明确不做（本 ADR 边界内）

不做**缩略图/压缩/上传**。本决定只解决"把已有图片读出来显示"；缩略图需要新依赖（sharp 等）或派生文件流水线，上传属写操作，两者都要另立规格与新 ADR。首版性能口径见 [CB-007 §1](../features/CB-007-images.md)（原图 + 懒加载，**不是**压缩缩略图）。

## 后果

### 好处

- 图片与 `data/` 一起备份、可以整体拷走；不进镜像、不进 git。
- 新增图片 = 放文件 + 重启，不需要改 JSON、不需要重建镜像。
- 无新增依赖、无新增进程、无新增端口；容器仍 `read_only: true`，图片运行期只读。
- 暴露面被白名单限制在"菜谱图片"这一种文件上，排障与审计都简单。

### 代价与必须接受的风险

1. **新增一条无鉴权的对外读路径**（`/images/*`）。与既有只读 API 同一信任模型：仅局域网、不公网暴露。若将来要公网访问，必须先补鉴权（那时新开 ADR）。
2. **原图直出**：没有缩略图，滚动浏览全部已有图片累计约 **56 MiB**（本机局域网可接受；真机若卡，另立规格做压缩）。
3. **局域网明文 HTTP**：图片内容可被同网段嗅探。与菜谱数据同样的前提，不因图片而新增风险类别。
4. **符号链接会被跟随**（`@fastify/static` 与扫描都不拒绝）：`data/images/` 里指向外部的符号链接会被提供出去。能创建这个链接的人已经拥有该目录的写权限，等同于可以直接投放文件，因此不额外拦截；**已实测并用测试固定**（见上方边界实测与 CB-007 §7）。

### 需要注意

- 容器与部署配置**不需要改**（图片目录本来就在 bind mount 里）；本次不执行任何部署（T3 需授权）。
- 缓存策略若将来改为带内容指纹的 URL，必须先解决"版本号与内容绑定"的问题（例如用内容哈希），不能直接用启动时的 mtime。
- `data/images/` 的清理/迁移属数据操作：本 ADR 不授权删除任何图片。

### 边界实测（2026-09-20，本机生产模式；完整记录见 [CB-007 验收](../verification/CB-007/CHECK.md)）

| 情形 | 实测结果 |
| --- | --- |
| 白名单内的图片 | `200 image/jpeg` + `no-cache` + ETag；带 `If-None-Match` → **304**（浏览器实测出现 304） |
| 缺失 / 未认下的文件（`nope.jpg`、`cover.png`、`notes.md`、`.DS_Store`、`step-99.jpg`、无对应菜谱的目录） | **404** + `no-store`，且不是 HTML |
| `/images`、`/images/`、`/images/<id>/` | **404**（不给目录列表） |
| 编码穿越 `%2e%2e` | **403**（插件拒绝非规范路径） |
| 字面 `..`（`/images/../equipment.json`） | 被 HTTP 客户端/浏览器先规范化 → 落到 SPA 兜底（200 HTML）；**body 中没有该文件的内容** |
| 大小写变体 `cover.JPG` | 403（macOS 大小写不敏感文件系统）；Linux 上会是 404 —— 两者都不是 200 |
| 符号链接（`cover.jpg` → 目录外文件） | **会被提供**：扫描把符号链接当图片收下（`isSymbolicLink()`）。能创建该链接的人已拥有 `data/images/` 写权限（等同可直接投放文件），故接受 |

结论：没有任何一条请求返回 `data/` 中白名单以外的文件内容。
