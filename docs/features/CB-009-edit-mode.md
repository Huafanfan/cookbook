## 1. 目标与非目标

### 目标（用户能观察到的结果）

1. 在菜谱详情页点**编辑**，能改这道菜的全部字段（菜名、别名、分类、标签、摘要、难度、份量、耗时、厨具、食材、步骤、小贴士、**来源**），保存后**列表与详情立刻显示新内容**（不需要重启）。
2. **改错了能退回去**：详情页能看到"改过 N 次"，能看某一版的内容，能**恢复到某一版**。
3. 内容纪律不放松：写进去的内容必须能过 `npm run check:data` 的同一套校验（含厨具/tag 词表）；不合法的改动被拒绝并指出**哪个字段**错了。
4. **两台设备同时改不会静默覆盖**：后保存的一方会看到"服务器上已经是另一个版本"，并自己选择怎么办。
5. 手机上也能改（至少能改用量、步骤文案这种小改动）：输入区够大、不横向滚动。

### 非目标

1. **不做图片上传/换封面**（另立规格；本次编辑界面里不出现图片字段）。
2. 不做多用户、权限、编辑者标识（局域网无账号，与 ADR-0003 同一信任模型）。
3. 不做实时协同编辑、不做合并 UI（冲突时只做"重载 / 覆盖"两种选择）。
4. 不做批量编辑、不做新建/删除菜谱（**新建与删除另立规格**：删除属 T3，需要明确授权）。
5. 不做富文本/Markdown（步骤就是纯文本，保持"一句话说清"的纪律）。

## 2. 用户场景与状态流

```text
详情页 → 点「编辑」
  → 表单预填当前内容（字段分组：基本 / 食材 / 步骤 / 其它 / 来源）
  → 改动（可随时「取消」；有未保存改动时离开会拦一下）
  → 点「保存」
      ├─ 服务端校验通过 + 版本没变 → 写入成功 → 历史 +1 → 回到详情页看到新内容
      ├─ 校验不通过（400）→ 停在表单，标出出错字段
      └─ 版本变了（409）→ 弹提示："服务器上已被改过"，两个选择：
             「重新加载（放弃我的改动）」/「用我的覆盖」
  → 详情页「改过 N 次」→ 历史列表 → 看某一版（只读）/ 恢复这一版（= 一次新的保存，历史保留）
```

## 3. 交互细节与状态

| 状态 | 表现 | 说明 |
| --- | --- | --- |
| 入口 | 详情页标题下方一个「编辑」按钮 | 不做"编辑模式开关"（那会让人不确定当前是否可写），点了就进编辑页 |
| 编辑页 | 独立路由 `/recipe/<id>/edit` | 便于从地址栏直达、刷新不丢（草稿仍在本地） |
| 字段分组 | 基本（菜名/别名/分类/标签/摘要/难度/份量/耗时）、厨具、食材（分组/名字/用量/单位/备注）、步骤（文案/小标题/时间/火候/提醒）、小贴士、来源 | 与 [DATA_MODEL](../DATA_MODEL.md) 的字段一一对应 |
| 食材/步骤编辑 | 每行一个条目，可**上移/下移/删除/新增** | 顺序 = 显示顺序（数据模型里就是数组顺序） |
| 必填缺失 | 保存时才报错，**在对应输入框下方**写清原因 | 不做"输入时立刻红"（打断输入） |
| 保存中 | 按钮禁用 + 文案"保存中…" | 防连点 |
| 保存成功 | 回到详情页，内容已更新 | 乐观显示 + 以服务端返回为准（失败则回退并提示） |
| 校验失败 | 停在表单，字段级错误 + 顶部一条汇总 | 服务端 400 的报错必须能映射回字段 |
| 版本冲突 | 顶部红色告警 + 两个按钮（重新加载 / 用我的覆盖） | **不允许静默覆盖**；覆盖时要再确认一次 |
| 未保存离开 | `beforeunload` + 站内跳转都拦一下 | 手机上误触返回很常见 |
| 草稿 | 表单内容按菜谱 id 存 localStorage（会话内），刷新后可恢复 | 只存草稿，不冒充已保存；保存成功即清掉 |
| 历史列表 | 时间 + 来源（手改/恢复/LLM 合并）+（可选）一句说明 | 数据来自 `data/history/recipes/<id>/` |
| 看某一版 | 只读展示该版全文 | 不做并排 diff（人工看两份成本高，但 diff UI 属另一个规格） |
| 恢复某一版 | 二次确认 → 以该版内容调一次保存（来源标记 `restore`） | **不删历史**；恢复本身也是一条新记录 |
| 手机端 | 输入框 ≥16px（避免 iOS 自动缩放）、点击区 ≥44px、不横向滚动 | 复用现有 CSS 变量 |
| 词表未载入 | 厨具/标签选择区显示"清单未载入，保存前请刷新"并**禁用保存** | 不能拿空词表把厨具清空（与 CB-002 同一纪律） |

## 4. 数据与接口变化

### 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/recipes/:id` | **响应新增 `revision`**（**文件字节的完整 SHA-256**）—— 保存时用它做版本守卫 |
| `PUT` | `/api/recipes/:id` | body **严格** `{ recipe, baseRevision, note? }` → 200 `{ recipe, revision }`；写前过 **zod + 内容检查（content-lint 的阻止性问题）**；不合法 → 400（带字段路径）；`baseRevision` 不符 → **409** `{ error: "revision_conflict", current, currentRevision }`；写盘/历史失败 → 503。**`recipe.id` 必须等于 URL 里的 id**（不允许靠改 id 另存）；**受保护字段**（`sourceRef`、图片派生字段）由服务端保留，客户端提交的同名值不被采纳；请求体过大 → 413；非同源 / 非 JSON → 403 / 415 |
| `GET` | `/api/recipes/:id/history` | 历史列表（倒序，按 `historyId` 定位，**不是按内容 revision**）：`[{ historyId, savedAt, source, note?, beforeRevision, afterRevision, outcome }]`，只返回元数据 |
| `GET` | `/api/recipes/:id/history/:historyId` | 某一条历史记录的全文（含 `beforeRecipe`） |

- 历史**不需要单独的"恢复"接口**：前端拿到旧版全文后走同一个 `PUT`（来源标记 `restore`）。少一个接口就少一处不一致。
- **恢复也过守卫**：恢复时提交的 `baseRevision` = 当前文件的 `revision`（不是旧版那份的），否则会静默盖掉别人刚做的修改。
- **409 后的"用我的覆盖"不是 force-write**：前端必须带上 409 响应里返回的**最新 `currentRevision`** 再提交；若在此期间又有人改，**继续 409**（可反复），草稿保留。
- 写入仍只在 `recipe-repository.ts` 里发生（**每菜谱一条串行队列**）；路由只做校验、同源/大小检查与响应。
- **写成功后的索引同步**：刷新该菜的内存索引、`/api/meta` 的分类/标签聚合（tag 可能被改）、图片索引（步骤数变了 ⇒ `stepImages` 要重算）与列表响应；客户端缓存（列表/详情）以服务端返回值为准。

### 步骤增删重排的后果（必须定规则，不能留着不管）

`step-N.jpg` 是**按位置**命名的，而完成标记按**下标**存在 sessionStorage → 一旦增/删/重排步骤，两者都会指错：

- **步骤图**：位置变了就是不匹配 —— 保存后由服务端重算 `stepImages`；编辑页在"这道菜有步骤图且步骤数/顺序被改动"时**明确提示**："步骤动了，步骤图按位置对不上，需要把 `data/images/<id>/step-N.jpg` 改成对应编号（服务端已按新步骤数重算可用的那些）"。**不自动删图、不自动改名**。
- **完成标记**：保存成功后，若步骤文案/数量/顺序变了，前端**清掉该菜谱的完成标记 + 计时状态**并提示"步骤改了，已完成标记已重置"（宁可重打勾，也不要让人以为某步做过了）。

### 数据文件

```text
data/history/recipes/<recipe-id>/2026-09-21T14-33-05Z-manual.json   # 被替换掉的那一版（全文）
data/history/recipes/<recipe-id>/2026-09-21T15-02-11Z-llm-merge.json
```

```json
// 菜谱文件里新增（可选，向后兼容）：updatedAt
{ "id": "ang-ci-yu-dou-fu-tang", "updatedAt": "2026-09-21" }
```

**向后兼容检查**：`revision`/`updatedAt`/`sourceRef` 都是新增或派生字段；旧菜谱文件一个字节都不用改，`npm run check:data` 仍全绿。

## 5. 失败、降级与边界

| 情形 | 行为 | 用户可见反馈 |
| --- | --- | --- |
| 校验失败（400） | 不写盘 | 字段级错误提示 |
| 内容检查未过（阻止性问题，如文案分钟数与 `minutes` 不一致） | 不写盘（与 `check:data` 同一套规则在服务端执行） | 字段级/条目级提示 |
| 版本冲突（409） | 不写盘，返回当前版本与 `currentRevision` | 明确两个选择 + 覆盖需二次确认；**覆盖要带最新 revision 重试**，可能再 409 |
| **外部写者同时改文件**（手工编辑器 / 脚本 / `scp`） | **不保证**能拦住（TOCTOU 窗口，见 [ADR-0005 §1](../decisions/ADR-0005-editable-recipes-and-history.md)）—— 写入前重读重比只降低概率，不是互斥 | 文档与编辑页写清"手工改文件请先停服"；发现 `revision` 变了就是 409 |
| 写盘失败（503，磁盘满/只读） | 内存索引不变（回滚） | "没能保存，内容未变" |
| 历史快照写失败 | **整次保存失败，当前菜谱文件不变** | "没能保存，内容未变"（宁可不保存，也不要"改了但留不下记录"） |
| 历史写了、当前文件替换失败 | 保留一条 `outcome: failed` 的历史记录（标明是失败的尝试） | 同上 |
| **替换成功之后**响应丢失/客户端断开 | 磁盘已是新内容 | **不得**说"已恢复原状"；提示"**保存结果未确认，请刷新查看**" |
| 步骤增/删/重排 | 服务端重算 `stepImages`；前端清掉该菜的完成标记与计时 | 编辑页提示"步骤动了，步骤图按位置对不上"+ 保存后提示"已完成标记已重置" |
| 菜谱文件被手工改坏（校验不过） | 该菜不被载入（现状），编辑入口对它不可用 | 详情页显示"这道菜的数据有问题"（复用现有跳过机制） |
| 词表（厨具/tag）未载入 | **服务端也拒写**（不只禁用按钮）；前端同时禁用保存并提示 | "清单未载入，刷新后重试" |
| 草稿恢复 | 草稿存 `{ recipeId, baseRevision, draft, savedAt }`；打开编辑页发现草稿 → 提示"继续编辑 / 丢弃草稿" | **恢复草稿不改写 `baseRevision`**（必须仍用它当初加载的那版）；localStorage 写失败要**可见**（不能静默丢草稿） |
| 大菜谱（20 食材 / 15 步骤） | 表单可滚动、不卡（纯组件，无虚拟列表） | 手机端实测 |
| 两人同时保存 | 先到者成功，后到者 409 | 见上 |
| 手工编辑器与网页编辑同时改 | 同上（哈希比对能发现） | 同上 |

## 6. 验收标准

- [ ] 手机（390×844）改一道菜的**用量与步骤文案** → 保存 → 列表与详情立刻显示新内容；**重启服务后仍在**。
- [ ] 电脑上改**食材顺序**（上移一步）与**新增一条小贴士** → 保存 → 顺序与内容正确。
- [ ] 详情页显示"来源"，且**来源可在编辑页修改**。
- [ ] 改完看"改过 N 次" → 能看到刚才那一版 → 恢复到上一版 → 内容变回旧版，**历史又多一条**（不丢记录）。
- [ ] 两台设备（或两个浏览器 profile）同时打开同一道菜：A 保存后，B 再保存 → B 收到冲突提示，选择"重新加载"能看到 A 的改动；选择"覆盖"能写入 B 的版本。
- [ ] 故意把食材名留空 → 保存被拒，提示定位到"食材第 2 条的名字"。
- [ ] **改 `id`**（直接构造请求把 body 里的 `id` 改成别的）→ 被拒（400），不会另存成新菜。
- [ ] **受保护字段**：请求里塞 `sourceRef` / `coverImage` / `stepImages` → 服务端保留原值（不被表单覆盖、也不被静默删掉）。
- [ ] 把厨具改成词表外的名字 → 保存被拒并列出可选值（与 `check:data` 同一套规则）；**词表未载入时服务端也拒写**（不只是按钮禁用）。
- [ ] 内容检查能拦住的问题（如步骤文案分钟数与 `minutes` 不一致）→ 保存被拒，与 `check:data` 报同一件事。
- [ ] **步骤增/删/重排**后：编辑页有"步骤图按位置对不上"的提示；保存后该菜的完成标记与计时被清掉并提示。（在临时目录上验）
- [ ] **并发与失败语义**（临时目录，不看真实数据）：同一道菜两个并发保存 → 串行执行、后者 409；
      历史写失败 → 当前文件不变；历史成功但替换失败 → 留 `outcome: failed` 记录；
      替换成功后响应丢失 → 再读文件是新内容且界面提示"结果未确认"而不是"已恢复原状"。
- [ ] 写盘失败（模拟只读数据目录）→ 界面回滚 + 明确提示；菜谱文件内容**未变**。
- [ ] 非同源请求（伪造 `Origin`）/ 超大 body → 分别 403 / 413，且**不写盘**。
- [ ] 未保存时点返回 → 有确认提示；刷新页面 → 草稿可恢复。
- [ ] `npm run typecheck`、`npm test`、`npm run check:data`、`npm run build` 全绿（记真实退出码）。
- [ ] 回归：只读接口、搜索/筛选/排序、图片、厨具匹配、点赞收藏**行为不变**。

## 8. 风险、回滚与依赖

- **风险 1（内容损坏）**：写接口把菜谱改坏。缓解：写入前过同一份 zod 校验 + 原子替换 + 历史快照 + git；测试覆盖"校验失败不写盘"。
- **风险 2（并发覆盖）**：两台设备/手工编辑器同时改。缓解：内容哈希版本守卫 + 409 + 不允许静默覆盖。
- **风险 3（无鉴权）**：局域网内任何设备可改。与既有信任模型一致（ADR-0003）；公网访问前必须补鉴权（新 ADR）。
- **风险 4（历史膨胀）**：每次保存一个文件。文本小（2–5 KB）；**不自动删除**（删除属 T3）。若将来要清理，另立规格 + 授权。
- **风险 5（导入覆盖）**：`scripts/import-howtocook.ts` 会直接覆盖文件 → 在 CB-010 落地前必须在文档/输出里标注；落地后统一走合并流程（ADR-0005 §7）。
- **回滚**：删掉 `PUT` 接口与编辑入口即可回到只读；已写入的内容留在文件里不受影响；`data/history/` 可保留（无害）。
- **依赖**：无新依赖（zod / React 已有）；依赖 CB-002 的词表（校验）与 ADR-0003 的写路径经验。

## 9. 实施拆解与顺序

1. **冻结写入协议（先做这个，先做测试）**：repository 的 `saveRecipe`（串行队列 → 重读重比 → zod + 内容检查 → 历史 → 原子替换 → 内存/索引更新）+ `revision`/`historyId`；用**临时目录**写并发、历史失败、替换失败、响应丢失、409、恢复的测试。
2. **接口**：`PUT /api/recipes/:id`（400/409/413/415/403/503 + 同源与大小限制）、历史列表/单条；`app.inject` 测试。
3. **导入器防误覆盖**：默认拒绝覆盖已存在菜谱（显式 `--overwrite-existing` 才覆盖）+ 文档写明"覆盖导入前先停服"。
4. **前端表单（基本字段 + 食材）**：独立编辑页、字段级报错、草稿（含 `baseRevision`）、未保存确认。
5. **前端表单（步骤 + 厨具 + 小贴士 + 来源）** 与排序操作 + 步骤变动提示。
6. **历史 UI**：详情页"改过 N 次"、只读某一条、恢复（走同一 `PUT`）。
7. **冲突 UI**：409 两个分支 + 二次确认 + 带最新 revision 重试。
8. **文档回填**：`DATA_MODEL`（`updatedAt`/历史目录/`historyId`）、`ARCHITECTURE`（写路径 + 每菜谱队列 + 同源/大小限制）、`README`（接口表）、`DEPLOYMENT`（备份含历史；覆盖导入前停服）、`ROADMAP`/`START-HERE`。
