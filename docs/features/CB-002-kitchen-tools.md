### 用户已拍板的决定（2026-09-19）

1. **默认厨具**：炒锅、砂锅、空气炸锅、烤箱、电饭锅 —— 后续可以补充新的厨具。
2. **缺件要标记出来**：需要的厨具我没有时，必须让我看见。
3. **不是只有一种工具能做**：菜谱可以声明可替代方案，**优先用我现有的工具**。
4. **（二次反馈）厨具必须是枚举值，不是自由文本**：我（使用者）只**勾选**我有的；厨具清单是受控词表，否则后面录入菜谱时名字无法统一（"不粘锅" vs "煎锅"永远匹配不上）。
   → 菜谱只能引用清单里的值，写错会在校验阶段直接报错，而不是静默变成"缺件"。

## 1. 目标与非目标

### 目标

1. 打开一道菜，**一眼知道现在能不能做**：厨具齐了 / 缺哪件 / 能不能换个工具做。
2. 缺件时，如果菜谱声明了替代方案，直接告诉我"**用你有的空气炸锅可以代替烤箱**"。
3. "我有的厨具"从**受控清单里勾选**：默认勾好 5 件，随时增删；清单本身是一份权威枚举，不允许自由填写名字。
4. **选菜时就知道**：列表页对缺厨具的菜打标记，不用点进去才发现做不了。

### 非目标

- **不做**采购建议（不推荐"你该买蒸锅"）。
- **不做**数量管理（不区分"一口不粘锅""两口炒锅"）。
- **不做**跨设备同步：我的厨具存在**浏览器本地**（手机为准）。跨设备同步需要写接口，属 M5（T2 + ADR），见 §8 演进路径。
- **不做**从菜谱内容自动推断厨具：靠菜谱数据显式声明。
- **不做**厨具的图片/图标库。
- **不做**在界面上新增厨具（那会重新引入自由文本）；清单是数据文件，扩展走文件 + 重启（见 §4）。

## 2. 用户场景与状态流

**场景 A（在厨房）**：想做红烧肉，先看厨具行——没有砂锅但有炒锅，看到"可用炒锅代替"，直接开做。
**场景 B（在超市/路上）**：翻列表挑菜，卡片上标着"缺烤箱"，直接跳过或点进去看替代方案。
**场景 C（添置新锅）**：买了蒸锅 → 打开"我的厨具"→ 加上蒸锅 → 所有菜立刻按新清单重新判定。

```text
列表页（卡片标"缺烤箱"）
   └─ 点开某道菜 → 详情页厨具行
        ├─ ✓ 全部拥有            → "厨具齐了"
        ├─ ~ 缺但有替代          → "需要 烤箱（没有），可用 空气炸锅 代替"
        └─ ✗ 缺且无替代          → "缺 烤箱" + "暂时做不了"
              └─ 点【我的厨具】→ 就地展开面板
                    ├─ 列出厨具词表全部条目，勾选/取消（没有自由输入）
                    ├─ 全选 / 全不选
                    └─ 立即保存并重新判定（不刷新页面）
```

## 3. 交互细节与状态

### 3.1 详情页厨具行

位置：菜名元信息下方（`厨具：…` 一行），替代现有的纯文本展示。

| 状态 | 表现 | 说明 |
| --- | --- | --- |
| ① 直接满足 | `厨具：炒锅 ✓、锅铲 ✓`，正常色 + 结论"厨具齐了" | 不制造焦虑 |
| ② 靠替代满足 | `厨具：烤箱（没有）· 用空气炸锅代替`，提示色（琥珀）+ 结论"可以做，用空气炸锅" | 这是"优先兼容现有工具"的核心 |
| ③ 有组完全不满足（组内一件都没有） | `厨具：缺 烤箱`，警示色（红）+ 结论"暂时做不了" | 明确劝阻，避免备料到一半发现 |
| 菜谱没写厨具 | 不显示这一行（也不显示"厨具齐了"） | 向后兼容，不制造噪音 |
| 还没设置过我的厨具 | 按默认 5 件判定，并提供"我的厨具"入口 | 首次使用即有价值 |
| 我的厨具为空 | 厨具行提示"还没设置我的厨具"，点击展开面板 | 不误判成"什么都缺" |

### 3.2 我的厨具面板（就地展开，不做弹窗）

面板就是**整份厨具清单的勾选框**：勾上 = 我有，取消 = 我没有。没有自由输入框。

| 状态 | 表现 | 说明 |
| --- | --- | --- |
| 默认 | 列出清单里全部厨具，按默认勾选 5 件 | 清单来自 `data/equipment.json`（经 `/api/meta` 下发） |
| 勾选 | 立即生效，页面上的厨具行与结论同步变化 | 改动立即写入 localStorage，**没有"保存"按钮** |
| 全选 / 全不选 | 顶部提供两个快捷按钮 | 换设备后快速重建 |
| 保存失败（隐私模式等） | 面板内提示"这次改动没能保存"，功能按内存中的值生效 | 不静默失败 |
| 清单为空（服务端文件缺失） | 面板提示"厨具清单未载入"，不显示勾选框 | 不误判成"什么都缺" |
| 本地存了清单里已没有的厨具 | 自动忽略该条 | 清单变更后不会残留幽灵厨具 |

### 3.3 列表页标记

| 状态 | 表现 | 说明 |
| --- | --- | --- |
| ① 直接满足 | **不显示**任何厨具标记 | 大多数菜都该是这种状态，不制造噪音 |
| ② 靠替代满足 | 小标"用空气炸锅代替"（提示色） | 提醒我"不用买锅也能做" |
| ③ 完全不满足 | 小标"缺烤箱"（警示色）；替代组全缺时**只显示第一件**（避免卡片文字过长） | 一眼跳过；完整说明在详情页 |
| 菜谱没写厨具 | 不显示标记 | |

## 4. 数据与接口变化

### 新增：厨具枚举清单（权威词表）

**文件**：`data/equipment.json`（与菜谱同级的数据文件，不进镜像；改完重启容器生效）

```json
{
  "tools": ["炒锅", "平底锅", "砂锅", "汤锅", "蒸锅", "高压锅", "空气炸锅", "烤箱", "微波炉", "电饭锅", "电饼铛", "烤盘", "蒸屉"],
  "defaultOwned": ["炒锅", "砂锅", "空气炸锅", "烤箱", "电饭锅"]
}
```

| 字段 | 说明 |
| --- | --- |
| `tools` | **权威词表**：厨具的合法取值。菜谱只能引用这里的值 |
| `defaultOwned` | 没设置过"我的厨具"时，默认勾选这几件（必须是 `tools` 的子集） |

**为什么是文件而不是界面输入**：自由文本一定会漂移（"不粘锅"/"煎锅"），让菜谱与厨具无法匹配。放进数据文件后：扩展清单只改文件 + 重启，不需要改代码或重建镜像。

### 菜谱字段（可选，向后兼容）

| 字段 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| `equipment` | 菜谱级 | `string[]` | **必需**的厨具（全部要有）；值必须来自 `tools` |
| `equipmentAlternatives` | 菜谱级 | `string[][]` | **可选**：每个子数组是"任选其一"的一组；值必须来自 `tools` |

**校验规则（本规格的严格性来源）**：

- 菜谱里出现清单外的厨具名 → **该菜谱文件校验失败并被跳过**，错误信息要能直接定位：`equipment[0]: 厨具"不粘锅"不在清单里，可选：炒锅、平底锅、砂锅…`
- `defaultOwned` 里出现清单外的名字 → 启动时告警并忽略该条（不阻止服务启动）
- `data/equipment.json` 缺失 → 服务照常启动，但厨具相关功能显示"厨具清单未载入"（菜谱里的厨具字段一并跳过校验，避免误杀全部菜谱）

```json
{
  "id": "ke-le-ji-chi",
  "equipmentAlternatives": [["炒锅", "电饭锅", "空气炸锅"]]
}
```

读法：主锅具可以是炒锅、电饭锅、空气炸锅中的**任意一件**；三者都不在词表里就会校验失败。

> 只声明**决定能不能做**的工具（锅、烤箱这类）。锅铲、碗、筷子这类通用工具不入清单，否则每道菜都会误报缺件。

**匹配优先级**（这就是"优先兼容现有工具"）：

1. 组内**优先命中菜谱第一个点名的**（我有炒锅就用炒锅，不提示替代）。
2. 只有第一件没有时，才用组内后面我有的那件，并提示"用 X 代替 Y"。
3. 组内一件都没有 → 该组**完全不满足**（此时不存在"替代"，因为没有可替代的东西）。

因此判定结果只有三种：**直接满足 / 靠替代满足 / 完全不满足**。

### 接口

- `GET /api/meta`：**新增** `equipment: string[]`（权威词表）与 `defaultOwned: string[]`，前端据此渲染勾选框。词表为空表示清单未载入。
- `GET /api/recipes`（列表）：`items[]` **新增** `equipment: string[]` 与 `equipmentAlternatives: string[][]`（缺省为空数组），列表页标记需要。
- `GET /api/recipes/:id`：直接返回两个字段，无新端点。
- 匹配全部在**前端**完成（依赖浏览器本地的"我的厨具"）；服务端只提供词表与菜谱数据。

### 向后兼容检查

- 两个字段都可选：现有菜谱文件不写厨具时，列表与详情都不显示任何厨具信息。
- 本次会给 `data/recipes/` 的 2 个样例补上真实厨具数据（含一个替代组）。
- `npm run check:data` 对旧文件仍通过。

## 5. 失败、降级与边界

| 情形 | 期望行为 | 用户可见反馈 |
| --- | --- | --- |
| localStorage 不可用 | 用 `defaultOwned` 在内存中工作 | 面板提示"改动无法保存" |
| 厨具名大小写/空格不同（`炒锅 ` vs `炒锅`） | 归一化后比较（去空白、忽略大小写）——**防御性**，正常数据不会出现 | 无 |
| `data/equipment.json` 缺失 | 服务照常启动，厨具功能提示"清单未载入"，菜谱厨具字段跳过校验 | 面板与厨具行给出提示 |
| `defaultOwned` 含清单外名字 | 忽略该条并告警 | 无 |
| 菜谱引用了清单外的厨具 | **该菜谱文件校验失败被跳过**，日志给出可定位的中文原因 | 列表页"未载入文件"提示（已有机制） |
| 菜谱提到的厨具我没有 | 视为"没有"，正常标记缺件 | 正常显示为缺件 |
| `equipmentAlternatives` 里有空数组 | 忽略该组 | 无 |
| 同一厨具重复出现 | 去重后判定一次 | 无 |
| `equipment` 为空数组或缺失 | 不显示厨具行/标记 | 无 |
| 我的厨具列表为空 | 不判定所有菜为"缺厨具"，而是提示先设置 | 厨具行提示"还没设置我的厨具" |
| 添加空白或只有空格的厨具名 | 拒绝添加 | 输入框不响应（无新增项） |

## 6. 验收标准

- [ ] 面板列出的是 `data/equipment.json` 里的**完整词表**，只能勾选，**没有自由输入框**。
- [ ] 词表未载入（文件缺失/格式错）时：**不给任何结论**，显示"无法判断"，且列表卡片不出现任何厨具标记。
- [ ] 首次打开（未设置过厨具）：按 `defaultOwned`（炒锅、砂锅、空气炸锅、烤箱、电饭锅）判定。
- [ ] 菜谱写了清单外的厨具 → `npm run check:data` 报错并指出是哪个字段、哪个名字、有哪些可选。
- [ ] 详情页展示 `可乐鸡翅`：厨具行显示我有的（✓）与没有的（标记），并给出结论。
- [ ] 对缺件但菜谱给了替代方案的菜：显示"可用 X 代替 Y"。
- [ ] 对缺件且无替代的菜：显示缺件 + "暂时做不了"。
- [ ] 点【我的厨具】就地展开面板：勾选/取消立即生效（页面上的厨具行与结论同步变化，无需刷新）。
- [ ] 勾选清单里的"蒸锅"（默认没勾）后，需要蒸锅的菜立刻不再报缺件。
- [ ] 取消勾选一件厨具后，依赖它的菜立刻变为缺件。
- [ ] 刷新页面后，"我的厨具"保持（localStorage 持久）。
- [ ] 列表页：缺厨具的卡片有标记；厨具齐全与未声明厨具的卡片**没有**标记。
- [ ] 菜谱没写厨具字段时：详情页与列表页都不出现任何厨具相关内容。
- [ ] 手机竖屏：厨具行不换行错乱、**面板每一行整行可点且行高 ≥ 44px**、无横向滚动。
- [ ] `npm run typecheck`、`npm test`、`npm run check:data` 全绿。

## 8. 风险、回滚与依赖

- **风险 1**（已在二次修订中解决）：自由文本导致名字不统一。现在厨具是**受控词表**，菜谱只能引用词表值，写错直接校验失败——从根上消除同义词问题。
  剩余代价：扩展词表要改 `data/equipment.json` 并重启容器（不需要改代码或重建镜像）。

- **风险 1b（独立复核 P1-1 后新增的纪律）**：替代组只证明"你有这件器具"，**不证明"这套步骤用它做得成"**。
  因此：**替代组里的器具必须能在同一套步骤下真正完成全部操作**（例如炒锅 ↔ 平底锅 ↔ 汤锅这类同操作方式的）；
  换成做法不同的器具（空气炸锅、电饭锅）必须**另写一份菜谱**，不能靠替代组混过去。
  违反时用户会看到"可以做"，然后照着"冷水下锅焯水"做，直接做坏菜——这是本项目最不能接受的错误类型。
  落地：写入 [`../DATA_MODEL.md`](../DATA_MODEL.md) 的内容规范，并在 `npm run check:data` 的说明里强调（人工判断，无法自动校验）。
- **风险 2**：浏览器本地存储意味着换手机/清缓存后需重设。缓解：`defaultOwned` 兜底 + 面板有"全选/全不选"。**演进路径**：M5 引入写接口时，把"我的厨具"存到服务端（届时需 ADR，因为引入写操作）。
- **风险 3**：列表页标记可能造成噪音。缓解：只在缺件时显示，齐全时不显示任何标记。
- **回滚**：新增字段可选 + 前端判定，回滚只需回退代码；数据文件无需回滚。
- **依赖**：CB-001 已引入 `equipment` 字段与详情页展示位置。

## 9. 实施拆解与顺序

1. **数据与判定**：`equipmentAlternatives` 字段（schema/types/summary）→ `kitchen.ts`（默认厨具、读写、匹配）+ 单测。
2. **详情页**：厨具行按匹配结果呈现（✓ / 缺 / 可替代 / 结论）。
3. **我的厨具面板**：就地展开、增删、持久化、失败提示。
4. **列表页**：卡片缺件标记 + 顶部"我的厨具"入口。
5. **内容**：给 2 个样例菜谱写真实厨具（含一个替代组）→ 真机验证 → 回填证据。

### 实现过程中发现并修正的问题

1. **同一 tick 连续两次改动会互相覆盖**（真 bug，验证时暴露）：面板原本用 prop 里的厨具列表计算下一状态，连续调用只生效最后一次。已把状态更新改为**函数式**（`apply(updater)`，内部用 ref 持有最新值），连续调用串行生效。
2. **卡片标记过长**：替代组全缺时显示 `缺炒锅 或 电饭锅 或 空气炸锅`，在卡片上太占地方。已改为**只显示第一件**（`缺炒锅`），完整说明留在详情页；规格 §3.3 已同步。
3. **样例数据误报**：一开始把 `锅铲` 写成必需项，但默认厨具里没有它 → 每道菜都会报"缺锅铲"。已改为只声明**决定能不能做**的关键锅具（通用铲勺不入清单）。
4. **厨具改为受控枚举**（用户反馈）：面板从"自由输入 + 删除"改为**只从词表勾选**；菜谱引用词表外的厨具**直接校验失败**（错误信息给出全部可选值）；`npm run check:data` 同步按词表校验，录入时本地就能发现写错。这条修正从根上消除了"不粘锅/煎锅对不上"的风险。
