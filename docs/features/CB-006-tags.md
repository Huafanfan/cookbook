## 1. 问题

- 371 道导入菜**零 tag**，只有自建 2 道菜带 4 个 tag → 筛选栏里"好几个 tag 没内容"。
- 若让 LLM 自由生成 tag，必然出现"快手 / 快手菜 / 省时"这类**同义变体**，筛选就废了（与厨具同一教训，见 CB-002）。

## 2. 做法

### ① tag 是受控词表（`data/tags.json`）

14 个 tag，**每个都写清判定标准 `when`**（给 LLM 一致判定的依据）：

```json
{
  "tags": [
    { "name": "快手", "when": "从备料到上桌大约 20 分钟以内" }
  ]
}
```

| 组 | tag |
| --- | --- |
| 场合 | 早餐 · 下饭 · 宴客 · 宵夜 · 便当 |
| 特点 | 快手 · 省事 · 新手友好 · 一锅出 · 清淡 · 重口 · 减脂 |
| 口味 | 辣 · 酸甜 |

**强制手段**：菜谱只能使用词表里的 tag —— schema 校验（`createRecipeSchema({ allowedTags })`），
写错直接报错并列出可选值；`check-data` 在**词表本身坏掉**时非零退出（与厨具同规则）。

### ② 逐道分类由 LLM 完成

- 输入：每道菜一行 `id | 菜名 | 分类 | 简介 | 食材`（371 行，分 4 批）
- 提示词约束：只能从词表选、每道 1–4 个、宁缺勿滥、按 `when` 判定
- 输出：`{菜谱id: [tag...]}`，由脚本**严格校验**（id 存在、tag 在词表内、1–4 个）后写回

**这是 LLM 判定值，不是原文数据**；分类依据（简介/食材/分类）都在菜谱里可复核。

### ③ 筛选栏顺序跟词表走

`/api/meta` 的 `tags` 改为**词表顺序**（而不是字母序），且只列出真的有菜在用的 tag —— 不再出现空 tab。

## 3. 非目标

- 不做 tag 的界面编辑、不做多层 tag 树。
- 不做用户自定义 tag（那会重新引入自由文本）。
- 不把"主料"做成 tag（分类已经承担了这条轴）。

## 4. 边界与失败

| 情形 | 行为 |
| --- | --- |
| `data/tags.json` 缺失/格式错 | 服务照常启动，**跳过 tag 校验**（不误杀 371 道菜）；`check-data` 非零退出 |
| 某道菜没有 tag | 允许（列表页仍显示，只是筛不出来）；本次分类 371/371 全覆盖 |
| LLM 给出词表外的 tag | 合并脚本拒绝该条并在报告里列出（本次 0 条） |
| tag 名重复 | 载入时去重 |

## 5. 验收标准

- [ ] 筛选栏列出 14 个 tag，**每个都有菜**（无空 tab）。
- [ ] 顺序按词表（场合 → 特点 → 口味），不是字母序。
- [ ] 点任一个 tag 都能筛出菜（如「减脂」16 道、「宵夜」10 道）。
- [ ] 菜谱写词表外的 tag → `npm run check:data` 报错并列出可选值。
- [ ] `data/tags.json` 缺失时服务仍能启动、`check-data` 非零退出。
- [ ] 371 道菜全部有 1–4 个 tag；0 条词表外取值。
- [ ] `typecheck` / `test` / `check:data` / `build` 全绿。
