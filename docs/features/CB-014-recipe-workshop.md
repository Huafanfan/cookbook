## 1. 目标与非目标

### 目标（用户能观察到的结果）

- 首页进入“创意工坊”，给出链接、文字、图片或混合材料，得到与现有菜谱格式兼容的可编辑草稿。
- 一份材料可以追加到同一草稿。例如公众号链接抓取失败后补截图，再补一句“我家实际用 300g 土豆”，无需重新开始。
- 能看出哪些信息来自材料、哪些由自己补充、哪些是整理建议、哪些还缺失；确认后才保存为新菜。
- 新菜保存后出现在列表、搜索与分类里，可用现有详情、计时、收藏、编辑和历史功能；刷新或重启后仍在。
- 材料与草稿保存在本地服务的数据目录，可在另一台局域网设备继续整理。最终仍是一道菜一个 JSON 文件。

### 首版范围

| 输入方式 | 包含的实际用法 | 首版处理方式 | 主要边界 |
| --- | --- | --- | --- |
| 链接 | 普通菜谱网页、公开文章、GitHub Markdown、从分享文案中粘贴的网址 | 提取可读正文或 `Recipe` 结构化数据，再交 DS 整理 | 只承诺公开可读取内容；平台适配要用真实链接验收 |
| 文字 | 复制食谱、聊天记录中的做法、自己的笔记、外文菜谱 | 粘贴、输入或读取 UTF-8 `.txt`/`.md` | 外文可整理成中文，保留原用量和单位；不自动换算份量 |
| 多张图片 | 小红书截图、长图、纸质书照片、手写菜谱、步骤照片、聊天截图 | 按用户顺序给 DS 多图识别与整理 | 手写、长图小字和纯操作照片需单独验收；不能保证读清所有图片 |
| 结构化文件 | 现有格式菜谱 JSON、单道 `Recipe` JSON-LD | 先确定性解析和校验；字段齐全时无需 LLM | 外部 ID、保护字段不直接作为新菜的系统字段采用 |
| 混合材料 | 链接 + 截图 + 文字补充；两种来源互相补全 | 同一草稿统一整理，逐项显示冲突 | 不把不同菜或不同版本的用量自动混合 |
| 手动录入 | 自创做法、没有外部材料的家庭菜 | 从空表单开始，复用现有菜谱编辑字段 | 不要求调用 LLM |
| 系统语音输入 | 用手机键盘口述做法，转成文字后提交 | 走文字入口 | 由手机系统提供；网页录音不在首版范围 |

图片首版接受 JPEG、PNG、WebP；允许桌面拖放、文件选择和浏览器提供的粘贴事件。手机提供相册/文件选择，并在浏览器支持时通过文件输入调用系统拍照。HEIC、GIF、直接剪贴板读取与长图自动切片不作首版承诺，未支持时给出可操作的转换/拆图提示。

### 后续扩展方向（不包含在首版实施授权中）

| 方式 | 推荐接法 | 成本与前置条件 |
| --- | --- | --- |
| PDF | 有文本层的先本地提取；扫描页渲染为图片后交 DS | 需要 PDF 解析/渲染与页数预算；初期可先用截图入口 |
| Word / HTML 文件 / 表格笔记 | 在本地提取正文或单道菜片段，复用文字流程 | 分别评估解析器；首版可复制正文。HTML 不执行脚本 |
| 录音文件 | 本地 ASR 转写 → 用户校对 → DS 整理 | 候选为 whisper.cpp；要测试中文食材词、数字、时长和服务器资源占用 |
| 视频或视频链接 | 可读说明/字幕 → 必要时本地转写、抽帧 → DS 文本与图片整理 | 要有实际获取权限、时间戳证据、时长/文件上限；不能把视频标题当完整做法 |
| 手机分享入口 | iOS 快捷指令把链接/图片交给工坊；PWA 分享目标按设备支持评估 | 需另验接口访问方式、系统权限与 HTTPS/浏览器条件 |
| 多菜批量材料 | 先识别多道菜并拆成独立草稿，逐道确认保存 | 避免误合并，不能一次未经审阅批量注入 |
| 从成品图/一句想法创作 | 显式“AI 创作”模式，所有推测与用量建议均标识 | 与忠实录入分开立规格；成品照片不能还原真实配方 |

### 非目标（明确不做，以及为什么）

- 首版不实现上述后续扩展，不新增音视频服务、浏览器自动化抓取或完整 OCR 服务。
- 不承诺任何网站链接都能抓取；不导入登录态、Cookies，不绕过登录、验证码或付费限制。受限内容可由用户提供文字或截图。
- 不自动修改或覆盖已有菜谱，不删除菜谱/草稿/原始素材，不开展全库批量导入。
- 不让模型直接写文件、调用工具、执行代码或决定磁盘路径。
- 不凭成品照片补成“有来源”的完整配方，不静默猜数量、份量、火候或时间。
- 不更换数据库、引入多用户账号或修改网络监听；不增加第三方云 OCR/搜索/语音服务。DS 是用户本次明确指定的 LLM 提供方。
- 网页正文中的图片不自动下载为正式封面；图片归属与使用条件按现有 [ADR-0007](../decisions/ADR-0007-reviewed-cover-sources.md)、[ADR-0008](../decisions/ADR-0008-open-photo-attribution.md) 处理。

## 2. 用户场景与状态流

主要在收集菜谱时使用：手机上从内容应用复制链接或选截图；电脑上粘贴正文、拖入图片并校对。厨房中可随手补一条实际做法，长文本校对不要求站着完成。

```text
首页“创意工坊” → 新建或继续草稿
  → 添加材料（可混用、补充、排序，尚未写入正式菜谱）
  → 点“整理成菜谱”
  → 提取材料 → DS 整理 → 显示预览与待确认项
  → 校对食材/步骤/来源，补齐必要字段，可选封面/步骤图
  → 点“保存为新菜” → 成功后打开新菜详情

任一步失败 → 保留已接收材料和编辑内容 → 补材料、重试或手动继续
检测到多道菜 → 先选一道 → 各自整理与保存，不自动混成一道
```

保存是单独的显式动作。点“整理成菜谱”、模型返回结果或离开页面，都不会将候选写入 `data/recipes/`。

## 3. 交互细节与状态

| 状态 | 表现 | 说明 |
| --- | --- | --- |
| 默认 | 简短介绍与“添加链接 / 粘贴文字 / 添加图片 / 手动录入”，下方可继续草稿 | 文件入口接受文本/JSON/支持的图片；不堆放多个不同流程 |
| 激活 | 每份材料显示缩略图或摘要、来源、顺序和处理状态 | 支持追加与调整顺序；从本次整理排除材料是取消引用，不删除持久化素材 |
| 空数据 | 提示先添加材料，或从空表单开始 | 输入只有标题/链接且没取到正文时，不假装已经读到做法 |
| 加载中 | 显示“读取材料 / 整理中 / 等待确认”，保留材料预览 | 不显示没有依据的百分比或固定完成时间；可退出后继续 |
| 出错 | 按材料显示抓取/识别失败，给出补文字、补截图、重试或手动继续 | 一份材料失败不丢掉其他材料 |
| 边界数据 | 小字看不清、资料不足、多道菜、数量冲突、缺份量分别提示 | 阻断项定位到字段，不只有笼统“失败” |
| 待审阅 | 手机上材料和菜谱用切换视图，电脑可并排看 | 重要数字旁能回看材料编号、原文片段或对应图片 |
| 保存中 | 锁定本次提交，重复点击只跟踪同一次保存 | 提交与恢复规则见 ADR-0009 |
| 已保存 | 显示新菜名称和打开详情入口 | 重新进入草稿可找到同一道已保存菜 |
| 结果未确认 | 网络断开时说明正在核实是否已保存 | 不自动新增第二道，不宣称磁盘一定没写入 |

### 整理与校对规则

1. 每个字段使用“来自材料 / 用户补充 / 整理建议 / 未知”的状态；不把模型自报的置信百分比当质量证明。
2. 已给出的原始用量保持原意。“适量”“少许”保持字符串；分阶段的盐、油等保留各组，图片重复段落去重不能误合并分阶段材料。
3. 不存在的可选用量、火候、准备/烹饪时间可以缺省；不能用 `0` 表示未知。步骤中明确的单一分钟数须与 `minutes` 一致；范围、多段时间按现有内容检查规则提示，用户选默认计时值。
4. 当前正式格式中 `servings`、`difficulty`、`category` 必填。草稿允许未知：份量缺失时留待填写；分类、难度可给“整理建议”，保存前用户确认。标签与厨具只用现有词表。
5. 用户的明确更正优先于来源，但保存更正依据。两份来源数字不同要展示冲突；“我想少盐”不能被擅自换算成一个精确克数。
6. 用户已编辑的字段，再次整理时以建议展示差异，不直接覆盖。来源发生变化后，旧任务结果不覆盖新草稿。
7. 若只有成品照片或食材摆拍而无做法，不生成假装有依据的步骤；提示补正文、步骤照片或手动写做法。
8. 一批材料包含不同菜时先选择候选。相同名字或相同来源与已有菜匹配时提示可能重复；用户可继续另存新菜，已有版本保持原样。
9. 上传截图默认只用于识别。首版正式配图采用用户自己的成品/步骤照片，确认对应步骤后才转换；需要署名的第三方图片须先完成 ADR-0008 的署名流程，不由工坊自动采用。封面和步骤图不由模型擅自绑定。
10. 来源展示保留原标题、作者（可获取时）和链接；“LLM 整理”描述处理过程，不替代内容作者或使用条件。

手机竖屏在 320px、390px 下无横向滚动，点击区域至少 44px；添加材料和补字段一只手可操作，数量、时间、缺项提示可读。进入做菜时沿用现有详情页，后续试做反馈仍记录到 [CB-001 反馈](CB-001-cooking-feedback.md)。

## 4. 数据与接口变化

| 变化 | 内容 |
| --- | --- |
| 菜谱文件字段 | 首版不新增 `Recipe` 字段；继续使用 `source` 展示来源，不将工坊材料伪装成 HowToCook 的 `sourceRef` |
| 草稿及素材记录 | 新增本地 `data/workshop/`；记录模型/提示词版本、来源、候选、审阅状态和创建结果。目录与提交协议以 ADR-0009 为准 |
| 共享类型与校验 | 工坊材料、允许缺项的候选、字段依据、草稿与接口类型只定义在 `src/shared/types.ts`；运行时校验只定义在 `src/server/lib/schema.ts` |
| 图片目录 | 采用配图仍进入 `data/images/<新菜 id>/cover.jpg`、`step-N.jpg`，由现有图片扫描与白名单托管；原始截图不进入此目录 |
| 写路径 | 新建仅经 repository；沿用正式菜谱 zod、词表和内容检查。存在同 ID 时拒绝创建，不使用现有 PUT 偷换成新建 |

最终正式文件仍可直接使用当前格式，例如以下人工构造的数据（不是实际导入）：

```json
{
  "id": "workshop-20261001-demo",
  "name": "土豆汤",
  "category": "汤",
  "difficulty": 1,
  "servings": 2,
  "ingredients": [
    { "name": "土豆", "amount": 300, "unit": "g" },
    { "name": "水", "amount": 500, "unit": "ml" }
  ],
  "steps": [
    { "text": "土豆切块。" },
    { "text": "加水煮至土豆熟透。" }
  ],
  "source": "用户提供的文字；创意工坊整理，已人工确认"
}
```

草稿里的来源材料、未知字段和待确认项不混入正式 JSON。可审计依据通过草稿的 `savedRecipeId` 关联新菜。

### 建议 API（批准前均为提案）

| 接口 | 行为 |
| --- | --- |
| `GET /api/workshop/capabilities` | 返回启用的输入格式、限制与 DS 配置可用状态；不返回密钥或完整环境配置 |
| `GET /api/workshop/drafts` | 返回草稿摘要，供跨设备继续 |
| `POST /api/workshop/drafts` | 创建空草稿，返回草稿 ID 与 revision |
| `GET /api/workshop/drafts/:id` | 返回草稿、材料摘要、待确认项和任务状态 |
| `POST /api/workshop/drafts/:id/sources` | 添加链接、文本或受限文件字节；链接添加阶段仅登记，按“整理”动作提取 |
| `PUT /api/workshop/drafts/:id` | 带 `baseRevision` 保存候选、顺序和材料选择；409 时返回当前草稿，不静默覆盖 |
| `POST /api/workshop/drafts/:id/analyze` | 带来源 revision 发起一次整理，202 返回任务 ID；重复请求复用当前任务 |
| `POST /api/workshop/drafts/:id/commit` | 带草稿 revision 与创建幂等键确认保存新菜；成功返回 recipe ID/revision |

素材访问采用只读的 `GET /api/workshop/drafts/:id/sources/:sourceId`，由记录查找字节；不接受客户端文件路径、不注册任意目录静态托管。API 错误码覆盖 400 字段错误、403 来源/同源拒绝、409 版本或 ID 冲突、413 超限、415 不支持格式、429 忙或上游限流、503 配置/持久化不可用。

**向后兼容**：旧菜谱、旧图片和已有用户状态不用迁移，现有读写接口保持原协议。新草稿有独立版本，不能要求旧数据增加工坊字段；首版不改 CB-010 的脚本模型与合并协议。

## 5. 失败、降级与边界

| 情形 | 期望行为 | 用户可见反馈 |
| --- | --- | --- |
| 链接登录受限、403、只有页面壳或提取不到食谱 | 保留链接，可加文字/截图后继续同一草稿 | “没有读到完整做法”，不宣称已分析整篇内容 |
| 链接指向内网/本机、危险跳转或超限 | 提取前拒绝，模型不接触此 URL | 提示换公开链接或粘贴正文 |
| 图片不支持、无法解码、体积或像素超限 | 拒绝该材料，其他材料保留 | 显示具体格式/上限及转换、拆图办法 |
| 图片字迹不清、长图丢细节 | 未知字段明确保留，不做确定值 | 回看原图并补信息 |
| 来源与模型结果数字不一致 | 标记待核对，不能仅靠 JSON 校验放过 | 指向用量/时间及材料依据 |
| 份量、食材或步骤缺失 | 候选可存草稿；正式保存受阻 | 定位缺项并允许手动补齐 |
| DS 未配置、401 或模型不支持图片 | 禁用受影响的整理能力，手工录入仍可用 | 显示配置原因；不切换到其他供应商 |
| DS 超时、限流、空内容、JSON 截断/校验失败 | 有界重试后保留草稿，不写正式菜谱 | 手工继续或显式再次尝试；任务预算见 ADR |
| 浏览器不支持粘贴图片/系统拍照 | 文件选择、相册、文字入口可用 | 对应按钮按实际能力展示 |
| 两台设备同时改草稿 | revision 冲突，不覆盖另一台的内容 | 重新加载/复制当前编辑内容后人工处理 |
| 快速重复整理或旧任务晚到 | 复用当前任务；按来源版本拒绝过期结果 | 当前任务/当前材料状态保持一致 |
| 重启时任务在执行 | 任务标为中断，已保存材料和编辑可恢复 | 用户决定是否重试，不自动重放收费请求 |
| 新建失败、响应丢失或磁盘满 | 按 ADR 提交点核实结果，已存在的菜不受影响 | 未提交可重试；已提交返回同一新菜 |

## 6. 验收标准

- [ ] **文本**：手机 390×844 粘贴一份材料，整理后数字、分组和步骤与原文一致；不需要看或编辑 JSON。
- [ ] **多图**：分别用平台截图、纸质印刷照片、手写照片和长图样例；记录每类成功/失败和所有数字错误。多张截图按顺序拼接，重叠文字去重；无法识别处不假装确定。
- [ ] **链接**：至少一个含 `Recipe` JSON-LD 的公开网页、一个无该标记但正文可读的网页、一个公开 Markdown；对实际常用平台分别用用户样例记录可用性。未实测的平台不得标记“已支持”。
- [ ] **受限链接**：抓取失败后补截图/文字，仍用同一草稿完成；错误不把网页标题转换成不存在的完整配方。
- [ ] **混合材料**：一链接、两图、一段用户更正一起整理，显示冲突与更正来源；更正数量只采用用户实际给出的值。
- [ ] **缺项**：原文没有份量、时间或用量时，草稿保持未知；保存前明确补份量，未给出的可选时间不生成 `0` 或猜测值。
- [ ] **多菜与成品照片**：包含两道菜的材料先选择；只有成品图时要求补做法，不生成假配方。
- [ ] **手动与 JSON**：空表单可直接新建；符合现有 schema 的 JSON 可确定性预览，跳过无必要的 LLM 请求。
- [ ] **再次整理**：用户改过两处后追加材料，不被旧/新模型结果静默覆盖；可审阅建议差异。
- [ ] **持久化**：上传素材、编辑草稿后刷新和服务重启，另一设备仍可继续；运行中的模型任务重启后不自动重放。
- [ ] **新建**：在隔离数据目录保存一次，新菜立即出现在列表、搜索、详情；重启后仍在。重复提交/响应丢失只得到同一道菜；ID 冲突不覆盖现有文件。
- [ ] **配图**：原始截图不成为封面；人工指定的配图生成合法 JPEG，与明确选择的步骤一致，原有图片展示路径可读。
- [ ] **失败语义**：图片准备失败不出现半份正式菜谱；正式提交后回执失败能恢复；磁盘/词表不可用时明确拒写，原有资产不变。
- [ ] **外联与输入**：密钥不在浏览器包、日志或数据文件中；私网/回环/IPv6 变体、DNS 重绑定、重定向均有防护测试；材料中的指令和代码不能触发工具或执行。
- [ ] **布局**：320px、390px、桌面 1280px 可录入；长来源、长食材名和错误提示无横向溢出；按真实手机记录添加材料、校对和保存体验。
- [ ] **检查**：代码落地后 `npm run typecheck`、`npm test`、`npm run check:data`、`npm run build` 均通过，并记录退出码。
- [ ] **回归与试做**：既有搜索、筛选、编辑、历史、图片、计时、厨具、收藏不回归；至少一道实际新菜试做反馈进入 CB-001 反馈文档，未试做不能称厨房体验已验证。

## 8. 风险、回滚与依赖

- **识别风险**：数字、单位、小字和手写是主要薄弱点。保留原材料与字段依据，技术校验不能代替人工校对；样例质量验证是独立验收项。
- **来源风险**：平台可读取性会变化。用通用提取与用户材料兜底，适配范围以真实样例为准；不把调用 DS 等同于模型已浏览链接。
- **成本与存储**：图片识别按内容计费，素材占本地空间；预算、队列与保留策略以 ADR-0009 为准。一次两张合成食谱截图实测用量见 §11；没有据此推算真实材料的平均费用或耗时。
- **回滚**：实现后的代码回退可关闭工坊；保留已创建的有效菜谱、正式配图、草稿和来源证据。不以代码回滚为理由删除用户数据。
- **依赖**：CB-009 的校验/编辑/写入经验、CB-007 图片托管、现有词表；新增解析和图片依赖的理由见 ADR。DS 配置须注入实际应用进程，Mac shell 测通不等于 Docker 已配置。
- **实施前样例**：建议按用户常用来源选公开链接、图片与混合输入作为验收集合；尚未收到偏好时，默认优先通用公开网页与截图，不锁定某一内容平台。

## 9. 实施拆解与顺序

1. 批准首版范围与 ADR，选定验收样例；先确定部分候选、字段依据、草稿版本和新建提交协议。
2. 空表单/标准 JSON → 草稿 → 正式校验 → 幂等新建，在临时目录打通保存与故障恢复。
3. 服务端 DS 客户端与文字整理：预览、缺项、数字核对、用户编辑与再次整理差异。
4. 图片选择/粘贴、多图整理与人工配图确认；验证实际截图和照片，不用色块结果替代 OCR 验收。
5. 公共链接提取与混合材料，优先通用 `Recipe` JSON-LD/正文/Markdown；受限页面直接进入补材料流程。
6. 手机/桌面端验收、回归、文档回填。用户已授权部署供 review；实际部署前完成备份，结果记入 DEPLOYMENT。
7. 基于真实使用，再分别立项 PDF/Word、录音、视频、系统分享、批量材料；不在首版顺手加入重服务。

## 附录 A：调研依据与结论（2026-10-01）

### A1. 当前项目观察

- `src/server/routes/recipes.ts` 有查询、PUT 编辑与历史接口，没有新建接口；现有写接口限制 256 KiB，不能直接拿来接受图片。
- `src/shared/types.ts` / `src/server/lib/schema.ts` 的正式菜谱需要名称、ID、分类、难度、份量、至少一项食材和至少一步；许多采集材料不满足这一完整性，需要独立候选。
- `scripts/lib/llm-merge.ts` 是 CB-010 三方合并客户端，使用 `IVAN_ONLINE_*` 与旧 Luna 配置；不能直接当网站的 DS 多模态客户端复用。
- 现有生产依赖提供 Fastify/React/zod；有 Node fetch；`jsdom`、`pinyin-pro` 目前是开发依赖。没有上传、正文提取、PDF、图片解码或 ASR 的生产链路。
- 项目没有真实 `.env` 文件（只有服务器示例）。本地 shell 的 `DS_BASE_URL`、`DS_AUTH_TOKEN` 存在，端点是 `https://api.deepseek.com/`；以实际请求验证配置，而非依赖另一个工具进程是否继承 shell 环境。

### A2. DS 可行性与小样结果

当前 [DS Vision 官方文档](https://api-docs.deepseek.com/guides/vision/) 明确 `deepseek-flash` 接受文本与图片；可用 Chat Completions 的 `image_url` 内容块传本地图片 base64，支持 JPEG/PNG/GIF/WebP。截图识别宜保留细节，`detail: low` 会缩至 512×512。由此建议首版直接用 DS 多模态，无需另一个云 OCR 提供方。

[DS JSON 输出文档](https://api-docs.deepseek.com/guides/json_mode/) 支持 `response_format: {"type":"json_object"}`，提示词仍需写明 JSON 契约；空内容和输出截断需要处理。JSON 合法不代表符合菜谱 schema 或数字准确，仍须本地校验与人工审阅。模型配置与能力以 [模型文档](https://api-docs.deepseek.com/quick_start/pricing) 为准，不能沿用过时型号或把 Pro 的能力等同于 Flash。

本次只发送人工构造的色块与虚构文字，不涉及现有菜谱或私有图片。配置只从环境读取：

| 测试 | 观测 | 解释 |
| --- | --- | --- |
| `/models` | HTTP 200；列出 Flash 与 Pro | 本地 API/key 可用，不代表网站已接入 |
| 虚构土豆汤文字 + 两张 96×96 色块 + JSON 输出 | HTTP 200；合法 JSON；份量 2、难度 1、土豆 300、水 500 的文字断言通过；双图颜色/顺序的严格断言未通过；总计 600 tokens | 当次没有保留具体颜色字段，无法据此定位失败原因；不能因 200 就宣称图片质量通过 |
| 两张 256×256 色块，`detail: original`，明确字段和值域 | HTTP 200；结果 `{"firstColor":"red","secondColor":"blue"}`；总计 467 tokens | 多图传参、顺序识别和 JSON 协议的简单复核通过；不是菜谱 OCR 验收 |

共两次小规模生成请求，返回用量合计 1067 tokens；没有据此估算真实菜谱平均价格或响应时延。文字与图片接口具备实施条件，真实配方提取准确率仍待样例。

本次核实的是文本与图片链路；没有验证 DS 原生音频、视频或 PDF 输入。后续按本地转写/解析/抽帧后的文本与图片接入设计，不将这些能力假定为已经可用。

### A3. 网页、文件、语音与系统入口

- [Google Recipe 结构化数据文档](https://developers.google.com/search/docs/appearance/structured-data/recipe) 定义了食材、分组步骤、份量、时间、作者等机器可读字段。网页优先使用它，缺失时再提取正文；多份 `Recipe` 需用户选一道。
- [Mozilla Readability](https://github.com/mozilla/readability) 可提取阅读正文，适合作为通用文章兜底。它不能绕过登录或让不可读的动态页面自动变成正文；其官方说明要求保持 jsdom 的脚本与远程资源加载禁用。
- [PDF.js](https://mozilla.github.io/pdf.js/) 提供本地 PDF 解析/渲染基础；文本 PDF 和扫描 PDF 需要不同处理。它是后续候选，本次没有安装或跑扫描识别。
- [whisper.cpp](https://github.com/ggml-org/whisper.cpp) 有 CPU/容器转写链路，可作为本地 ASR 候选；中文数字和食材名准确率、目标服务器吞吐与额外运行成本需要单独测试。
- [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) 要求安全上下文。手机访问当前局域网 HTTP 地址不属于 localhost，网页直接录音不能作为默认保证；系统键盘语音输入、系统录音后上传是可替代路径，不必先更改站点监听或证书。
- [MDN share_target](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target) 表明系统分享接收依赖安装后的 PWA 和浏览器支持，兼容性有限；手机快捷指令与 PWA 分享入口应按实际设备另验。

### A4. 优先级假设

在用户尚未说明常用内容平台时，推荐先覆盖“公开网页、粘贴文字、多图、混合材料”，并给每种输入保留手动补充与确认保存出口。小红书、公众号、B站、抖音目前都没有用户提供的真实样例；这里没有将其中任何一家标记为已适配。
