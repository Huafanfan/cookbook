## 1. 目标与非目标

目标：扩大真实照片覆盖，先检索与当前缺图菜谱对应的开放许可图片；这一批先审核常见菜、早餐、主食、汤与饮品候选，采用能确认的素材。仅在网上来源检索未找到合适图片时考虑 AI，沿用 ADR-0007 的明确示意标识。

不要求本批为全部剩余菜谱套图；不覆盖已有封面，不改菜谱食材/步骤，不部署、不推送。应用运行仍只加载本地素材，不依赖在线图片。

## 2. 用户场景与状态流

手机或电脑浏览菜谱：无图卡片 → 本地新增审核通过的图并重启 → 卡片与详情出现对应照片。需要看出处时：首页底部“图片来源与许可” → 本地静态署名页 → 返回首页。

## 3. 交互细节与状态

正常、无图、加载与失败状态沿用 CB-007。署名页采用清楚的中文表格，列出菜谱、作者、原文件页、许可链接与修改说明；手机窄屏可滚动查看宽表格，返回入口和首页链接点击区至少 44px。

来自其他人的照片仅代表这类菜品外观，不能宣称是当前菜谱的实际试做。以主要食材、做法与成品外观一致为准；明显多出主要配料、菜品类别错误、实物不清楚的图不采用。

## 4. 数据与接口变化

- 菜谱 JSON 与接口字段：无变化，不需迁移。
- 图片：继续用标准 JPEG 与既有图片扫描，不覆盖已有资产。
- 静态署名页：Vite 复制 `public/image-credits.html` 到前端产物；Docker 构建阶段同步复制 `public/`，避免容器构建漏掉署名页。生产服务沿用已有静态托管，无新增 API、依赖、端口或部署方式变化；本轮不构建/启动服务器容器。
- 作者、原文件、许可与修改说明的权威位置为署名页；素材哈希、尺寸、审核、检查证据的权威位置为 CHECK。引用关系避免重复维护。

## 5. 失败、降级与边界

来源访问限流则降低请求频率并换用文件元数据查询；不因失败立即生成 AI。许可不明、与菜谱不符或解码失败则不采用。目标已存在则保留旧图。网页离线仍能显示本地照片与署名内容；外部原图/许可链接只在主动点击时访问。

## 6. 验收标准

- [x] 逐张审图并对照主要食材与做法，记录采用/拒绝理由。
- [x] 采用图的许可、作者、文件页和修改说明完整，可从首页访问署名页。
- [x] 最终图片可解码为 JPEG、长边不超过 1600px、单张不超过 500KiB；仅新增图片。
- [x] 所有既有菜谱与旧图片集合哈希不变。
- [x] 新图片在本地列表和详情可见，HTTP 返回真实 JPEG，手机与桌面无破图。
- [x] 署名页、返回首页和新增首页入口在手机、桌面可用。
- [x] typecheck、test、check:data 通过；没有实测则不记为真机或厨房验收。

## 7. 测试要点

素材逐张检查；复用现有图片加载/路由测试；本地 HTTP 字节核对；手机与桌面搜索、卡片进入详情及署名页链接实测。新增静态链接不编写镜像式单测。

## 8. 风险、回滚与依赖

照片可能来自餐馆或其他人的做法，只在主要食材与外观吻合时采用，不替代试做。若需撤回，将本批图片移到备份位置并重启，保留旧资产。依赖既有 CB-007 与系统 JPEG 转换工具。

## 9. 实施顺序

盘点与基线 → 公开来源检索 → 候选图与做法审核 → 新增图片和署名页 → 本地验证 → 回填证据。

## 10. 文档影响与实施前复核

已读 START-HERE、AGENTS、ARCHITECTURE、DATA_MODEL、CB-007、CB-012、ADR-0004/0007。目录与运行架构无冲突；开放许可署名在 ADR-0008 明确。用户本轮直接授权其他来源图片，本规格在导入前达到 `accepted`。完成后更新功能索引、数据模型的引用和当前本地状态。

## 11. 实现与验证证据

新增 20 张网络真实照片，本批未调用 AI；来源署名页与首页链接完成，Dockerfile 包含静态素材复制。三项必需检查及构建通过，280 项测试通过；本地 20 个图片响应与磁盘字节一致，手机与桌面共 40 条卡片进入详情的路径及署名页往返通过。旧资产摘要不变，裁切复核后两张改选并重验。素材身份、逐张理由、哈希和运行证据见 [CHECK](../verification/CB-013/CHECK.md)。未构建 Docker 镜像、未部署、未做用户观感或厨房验收。
