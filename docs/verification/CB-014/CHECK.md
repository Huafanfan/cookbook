## 实际 DS 与浏览器

使用原生 Chrome、生产前端和实际 Fastify 服务，绑定 `127.0.0.1:4313`；所有菜谱/素材均在临时隔离目录，保留一份基准菜验证不被覆盖。

1. 从空草稿填写土豆汤，确认保存；验证详情、分类/meta、刷新恢复。
2. 用 Chrome 渲染两张中文食谱截图：第一张为番茄蛋花汤用料（番茄 200g、鸡蛋 2 个、水 500ml、盐适量、2 人份），第二张为三步做法（煮番茄 3 分钟）。这是合成食谱截图，不是手写/真实纸书照片。
3. 添加两张图并输入“我实际用水 600ml，保持原文的 2 人份；不要猜没有写明的时间”，通过本地环境指定的真实 `deepseek-flash` 整理。
4. 断言番茄 200g、水 600ml、份量 2、步骤等待 3 分钟；未给出的整道菜准备/烹饪时长留空。此次请求返回用量 3130 tokens（prompt 2185、completion 945）。这是单次证据，不是平均费用/时延基准。
5. 校对保存后验证详情、工坊回执；同幂等键重试返回相同 ID，最终仅基准菜 + 两道测试新菜。原有基准菜不变。
6. 1280、390、320 像素浏览器验证：无水平溢出，手机重新打开结果默认显示菜谱草稿；控制台错误 0。

实际接口曾暴露两类问题并修复：模型给出对象 evidence/字符串 unresolved，先无损形状归一化再校验；生成期间旧表单编辑覆盖结果，改为任务期间锁定编辑，保留手机切换入口。组件及同一真实链路复验通过。

服务器真实网络检查发现 Node 22 的自动地址选择会向自定义 lookup 请求地址数组，原单地址回调无法兼容；已在目标 Node 22.23.2 复现 `ERR_INVALID_IP_ADDRESS`，指定已校验地址的 family 并关闭自动地址选择后同一公开地址返回 200。修复后的离线回归使用本机 TCP server，验证实际 Node 连接和原 Host；来源测试 13 项通过，完整 345 项回归通过。最终镜像的公开提取复验见部署记录。

尚未验证：真实手机相册/拍照/粘贴，手写与长图小字，用户常用的小红书/公众号等链接，最大图片/排队上限的负载表现，真实材料的平均费用/吞吐及新菜试做。这些保留为后续使用反馈，不以自动化测试代替。

### 既有功能的本轮实测

1. 手机尺寸从空草稿手动填写土豆汤：2 人份、土豆 300g、一步做法。缺项及未审阅时保存按钮禁用，自动保存后刷新能恢复；切到菜谱视图核对并保存，实际打开新菜详情，用量与份量一致。
2. 文字笔记能加入材料；本机 URL 被拒绝且已添加文字保留。公开 URL 能登记为另一份材料，刷新后两份材料都在。此处验证添加与持久化，没有抓取该示例页面或调用 DS。
3. JSON 文件选择器能够打开，但 Chrome 自动设置文件因扩展未获 file-URL 访问权限而受限。本轮没有扩大扩展权限；改用同一临时服务的来源 API 输入样例，浏览器继续验证整理、校对与保存。文件选择后的传输链路未在本轮浏览器完整复验，不能称已通过。
4. JSON 候选丢失 `steps[].minutes: 3`，保存时内容校验阻止缺失计时的菜入库。修复的回归与同一样例复验记录在下节。
